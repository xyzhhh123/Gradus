# Reasonix 专题：不压缩，只搬移

横向对照见 `context_reference.md`；可核对的路径行号见 `context_evidence.md`。本文只讲这一家。

选它单独成篇，是因为它的思路和其它六家都不在一个方向上：别人在问「这段历史怎么变短」，它在问「这段历史搬到哪去」。

---

## 0. 一句话

历史一个字都不删，只把已经移出视野的那一段**导出成一个文件**，在上下文里留一条指针。模型想看就自己去读。

## 1. 三层结构

```
账本（canonical transcript）
  └─ 会话里的完整消息列表，只追加，永不压缩、永不替换
     ① 全量：被移走的内容也在里面
     ② 唯一权威：任何副本都可以丢，它不能丢

检查点（CompactionState）
  └─ 一个数字 + 一串元信息：折叠到第几条、归档文件是哪个、投影版本、哈希

投影（模型每轮真正收到的）
  └─ = 已有视图 + 账本中「未被覆盖」的部分
```

模型看到的永远是投影。账本它看不到；归档文件只有拿着路径才能读。

这三层分开的直接后果：**压缩不改变真相，只改变视野**。要回退、要审计、要重开，账本一直在。

## 2. 六个机制

### 2.1 什么时候折叠

**触发线 = 窗口 × 90%**，每次构建请求前判一次。

一个刻意的取舍：**输出预算不参与触发线**。代码注释的意思是「输出会在发送时裁，绝不能让它把压缩提前」。这与 hermes（先扣输出预留再乘比例）正好相反。

除自动触发，还有手动命令，以及溢出/强制路径（后者可以豁免部分接受条件）。

### 2.2 在哪里切

两条硬规则：

1. **头部只保 system 提示**。除它之外，任何对话消息都可以被搬走。
2. **结尾只能落在「所有工具调用都已拿到结果」的位置**。

第二条的理由：切在未闭合的调用上，provider 会收到一个永远等不到结果的调用，直接报错；恢复时也说不清那个操作成没成。

**当前这一轮被钉住**：按「活跃轮开始时间」标出的那条用户消息，以及它牵涉的工具组，都不许动。所以真正能搬的，是「上一轮结束」到「这一轮开始」之间那一段。

### 2.3 产出什么

两样：**一个文件** + **一条指针**。

**文件**：把那段消息逐字渲染成文本，用内容哈希命名（`fold-3f9a2c81b4d7.md`），放在会话旁边的输出目录。

- 一次折叠一个新文件，**不是往同一个文件里追加**；
- 内容相同则落成同一个文件（幂等）；
- 写不进去就失败，**不降级成摘要**。

**渲染器只写四类行**，这一点决定了归档的边界：

```
[user]         内容
[assistant]    内容 + [assistant calls 工具名] 参数
[tool 工具名 result] 结果正文
[system]       内容（实际不会出现，折叠从 system 之后开始）
```

文件名里的哈希算的是这四类渲染后的正文，所以**归档不是账本的等价副本**：

| 账本有 | 归档里有吗 |
| --- | --- |
| 正文（谁说了什么、调了什么、结果如何） | 有，逐字 |
| `local_only` 内容（用户自己敲的 shell 输出、被打断的半截推理、界面动作） | **没有**（渲染器直接跳过） |
| 系统提示 | **没有**（折叠范围从它之后开始） |
| 工具调用 id | **没有**，只剩工具名 + 顺序 |
| 执行状态、退出码、耗时、token 用量、来源标记、决策回执 | **没有** |
| 图片等非文本内容 | **没有** |

所以准确的说法是：**正文无损，元数据与多模态有损。** 归档的定位是「给人和模型读的渲染」，不是「账本的备份」。

（补一句边界：缺调用 id 只影响「通读整段档案重建当时发生了什么」，不影响关键词检索——grep 只关心命中哪一行，不关心它属于哪次调用。）

**指针**：一条用户消息，包在 `<compaction-summary>` 里，告诉模型：前面 N 条已搬走、搬到哪、用 read_file 或 grep 读、**不要猜它的内容**，以及（可选）用户要求重点保留什么。

### 2.4 保留什么

只钉住**当前这一轮**的用户消息，再沿工具组往外扩：被保留的调用带上结果，被保留的结果找回调用。

没有「保留最近 N token」这种预算。理由是工具调用和结果不可拆，按轮次天然对齐。

### 2.5 值不值得

折叠不是「触发就做」，是**提案 + 审批**：

| 检查 | 规则 | 能不能豁免 |
| --- | --- | --- |
| 更小 | 折完必须比原来小 | 不能 |
| 落到线以下 | 必须低于触发线 | **永不豁免**（理由：压完还在线上，只买到下一次折叠） |
| 不超过一半 | 常规不超过窗口 50% | 强制/溢出时可豁免 |
| 前缀已超一半 | 要求至少省 25% | 同上 |
| 攒够了没有 | 二次折叠要求新增闭合历史达到窗口 10%（下限 3.2 万、上限 9.6 万，再夹窗口一半与触发线一半） | 应急时豁免 |
| 有没有可折的 | 至少 2 条 | — |

这是它与其它六家最不一样的地方：**把「什么时候折叠」从「快满了」改成「攒够了才值得付一次全款」**。

### 2.6 怎么找回来

两条完全不同的路，**不共用寻址**：

| | 查哪 | 怎么查 | 返回什么 |
| --- | --- | --- | --- |
| 召回工具 | **账本** | BM25 词频打分（不是向量，没有 embedding） | `#n` 地址 + 240 字片段 |
| 文件工具 | 归档文件 | grep / read_file | 原文 |

召回还能按 `#n` 直接读回原文，并有每代预算（窗口的 10%，下限 2000 token）；超了**整段拒绝**，不截断——半段回忆会被当成全部。

设计上的引导顺序是：**上下文里先找 → 有地址就读归档文件 → 地址丢了才回账本搜**。第一层有代码保证（召回会拒绝「还在上下文里」的地址，让你直接读上下文），后两层只是指针里的一句建议。

## 3. 为什么缓存命中率高

不是因为它优化了缓存，是**它没破坏前缀**：

- 历史只追加，从不回头改写；
- 易变信息（时间、任务进度、宿主上下文）每次现算挂尾部，不写进历史；
- 折叠是唯一的断裂点，而频率被接受条件压住。

有个反直觉的账：折叠看起来是「全量失效」，但折完上下文从 185K 掉到 12K，**重读的是 12K 而不是 185K**。所以折叠往往比继续跑一轮「全命中」还便宜——断裂的代价与断裂后的规模成正比，而折叠恰好把规模砍掉了。

## 4. 十六个容易搞混的点

这是把一次深入问答里的岔路整理出来的，每条都踩过。

| # | 容易以为是 | 实际是 |
| --- | --- | --- |
| 1 | 账本 = 上下文 | 账本是完整消息列表；「上下文」指投影，每轮现拼 |
| 2 | 归档 = 有损压缩 | 归档是「搬移」不是「压缩」：token 少了，正文没少（元数据会丢，见 #14） |
| 3 | 每次折叠往同一个文件追加 | 一次折叠一个新文件，按内容哈希命名 |
| 4 | 指针会一代代累积在上下文里 | 旧指针被下一代折叠吃进档案，视野里永远只有一条 |
| 5 | 归档文件里只有原文 | 开头还有上一代指针，「链条」藏在正文里 |
| 6 | grep 能从账本里检索 | grep 只查文件；查账本的是召回工具 |
| 7 | 召回是向量检索 | 是 BM25 词频打分，纯词法，没有语义 |
| 8 | 召回地址是行号 | 是账本里的消息序号；「是否已折叠」靠比已覆盖条数 |
| 9 | 检索结果不会被再归档 | 会：它作为普通工具结果，下次折叠被再写一份 |
| 10 | 归档会破坏前缀缓存 | 不会：追加在尾部；破坏前缀的是「改写」，它从不改写 |
| 11 | 归档文件 = 落盘文件 | 两回事：归档是一段历史，落盘是一次工具输出；同目录、不同用途 |
| 12 | 账本里的东西模型都能看到 | 账本里有 `local_only` 内容（用户私密命令输出、半截推理），永不给模型 |
| 13 | 折叠很贵（全量失效） | 折完只剩 12K，重读 12K 比继续跑一轮 185K 全命中还便宜 |
| 14 | 归档 = 账本的等价副本 | 只是「给人读的渲染」：正文逐字，但 `local_only`、系统提示、元数据、图片都不在里面 |
| 15 | 模型看过后再决定要不要把检索结果放进上下文 | 没有这个环节：调用一发出，结果必然进账本；进去多少由代码裁 |
| 16 | grep 整个目录 ≡ grep 某一个文件 | 整目录会把跨代重复的内容一起命中：token 翻倍，还可能把同一段误读成两次事件 |

补充五条：

- **指针不占空间**：约 120 token，可忽略。
- **归档之间不重复正文**：只传指针，不传内容。
- **但内容副本会重复**：检索结果、落盘输出都会被再归档，同一段文字可能出现在多个档案里。
- **重复的唯一规避方式**：grep 指定单个文件，或改用召回（查账本，按位置去重，天然不会重复）。
- **谁决定进上下文**：模型决定「要不要调、查多窄」（路径、模式、条数）；代码决定「进去多少」（上限、过滤、渲染）。模型没有「预览后反悔」的机会——它看到结果的方式，就是结果已经在上下文里。想做到「先看再决定」，只能靠代码模式（脚本内调工具，中间结果不回灌）。

## 5. 它没做好的四件事

### 5.1 数据层：用「复制」模拟「投影」

账本是唯一真相，但模型读不到它；为了让模型能读，它把一段**导出成文件**。

要的是「同一份数据的另一种视图」，做出来的却是「另一份数据」。视图是映射，副本会漂移、会膨胀、会被删。

后果：同一内容存在于账本和归档；检索结果再被折叠时又复制一次；大输出落盘和归档各存一份。

### 5.2 寻址层：两套体系并存且不对齐

召回用「消息序号 #n」，文件用「路径 + grep」，两者没有共享索引。折叠边界一变，两套地址的对应关系要靠人或模型自己维持。

而且档案按内容哈希命名，目录里按字母序排——**与年代无关**，文件系统层面根本没有「从新到旧」这条路径。

### 5.3 保留层：只有「活跃轮」一个维度

用户说的「别动 token 刷新逻辑」这类约束，和一条无关闲聊地位相同，一起被搬走。而约束恰恰 grep 不出来——它不体现在文件名或函数名里。

摘要派在这里反而占优：hermes 的十一个栏目、Claude Code 的九节里，都有「约束与偏好」这一格。

### 5.4 治理层：写完没人管

归档文件写进目录后没有生命周期：没有留存期、没有配额、没有清理。会话越长，磁盘越多。

（这一条是缺口，不是取舍——没找到任何清理逻辑。）

## 6. 一条它做对的取舍

「缺失通知」靠一句自然语言：指针里写「不要猜它的内容」「继续之前先恢复目标和决策」。

这是提示词约束，不是结构约束，模型可以无视。但要做成结构约束（固定的系统提示条目 + 强制工具调用），代价是**每次折叠都要改前缀**——而它现在用「插一条消息」的方式，恰好缓存友好。

**结构化的缺失通知** 与 **前缀稳定** 天然冲突。它选了后者。这个选择我认为是对的，只是要承认：它把可靠性押在了模型服从性上。

## 7. 对 Gradus 的取舍

**可以借的三条**

1. **接受条件**：给压缩加一道「值不值得」的检查，尤其是「二次压缩要等攒够」——它把成本从「触发即付」变成「攒够才付」。
2. **边界可查**：每次折叠留一条记录（触发方式 + 压缩前规模），事后能回答「这次移走了什么」。
3. **易变信息放尾部**：这是每轮都在省钱的动作，比压缩更划算。

**不该照抄的两条**

1. **用文件副本代替视图**：Gradus 已经在为「两套投影逻辑」付代价，再引入文件副本只会让真相更多份。
2. **只有单一保留维度**：Gradus 要处理多 agent 的工作产物，至少得有「活跃轮 + 语义角色」两个维度。
