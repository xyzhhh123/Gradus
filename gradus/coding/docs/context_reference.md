# 上下文管理：七种思路

这篇讲一件很具体的事：**当一个对话长到装不下时，不同 agent 怎么处理**。

不解释代码，不讲实现细节。只讲每个选择要解决的问题、代价是什么、以及为什么不同团队会得出不同答案。

对照的七家：codex、hermes-agent、learn-claude-code、pi-agent、deepseek-reasonix、DeepSeek Harness（下称 DSH）、Claude Code。前六家的做法可以从源码读出，Claude Code 是闭源产品，只能从公开发行物的行为里观察——这一点在最后单独说明，不混进结论里。

需要核对具体数值与出处的，看 `context_evidence.md`。

---

## 0. 从一个场景说起

你和 agent 聊了两个小时。它读了四十个文件，改了三十个，跑了十几条命令。现在这段历史有 200 万 token，而模型的窗口只有 20 万。

这时候你必须做一件事：**让后面的对话还能进行下去，同时不把那两小时白费**。

所有方案都在这个矛盾里挣扎。区别只在于：他们愿意丢什么、怎么丢、丢完之后还能不能捡回来。

## 1. 先认清三条约束

**窗口是硬约束。** 超过就报错，没有商量余地。所以每套方案都有两条防线：一条防止接近上限（压缩），一条在装不下时保命（兜底）。

**注意力是软约束。** 塞满 20 万 token 和用好 20 万 token 是两件事。一条三小时前读到的、与当前任务无关的文件内容，占着位置但没有价值。这也是为什么几乎所有实现都对「工具输出」特别苛刻——它们又长又少被复用。

**缓存是时间的函数。** 同样的前缀，第二次请求比第一次便宜一个数量级；一旦你改写历史，前缀就变了，从改动点往后全部重算。这条约束决定了压缩的真正成本：**压缩不是免费的，它是要付一次全款的操作**。

第三条最容易被忽略，而它恰好是各家的分水岭。

## 2. 第一问：什么时候动手

各家定的线不一样，但可以归成四种尺度：

| 尺度 | 谁用 | 性格 |
| --- | --- | --- |
| 裸窗口的百分比 | codex（90%）、reasonix（90%）、DSH（80%） | 与模型能力无关，跨模型行为一致 |
| 窗口减一个固定余量 | pi（16,384）、Claude Code（13,000） | 给输出留位置，余量就是「一次回答最多能多长」 |
| 窗口减预留再乘比例 | hermes | 最保守：先扣输出，再按比例，还有 64K 下限与 85% 上限 |
| 固定字符数 | learn-claude-code（50,000 字符） | 无视模型，教学够用 |

数字本身没那么重要，**基数才是**。同样是「90%」，codex 和 reasonix 都以裸窗口为基数，而 hermes 要先减掉输出预留——在 20 万窗口上，这两者差了 1.6 万 token 的体感。

还有一个反直觉的事实：**压得越晚越省钱**。每次压缩都要重建整份前缀缓存，压三次就是三次全款。所以压得晚 = 少压一次 = 少付一次钱。但压得太晚，一旦某个回合突然爆量（比如一次读了五个大文件），就来不及了。

这就是为什么 pi 和 Claude Code 把余量压到 13K–16K，而 hermes 要留 64K 下限：**前者赌「回合不会突然爆量」，后者在防这件事**。Claude Code 敢压到 13,000，是因为它在前面还有一层微压缩兜着（见下一节）。

时机有四个位置：回合开始前（主流）、回合进行中（处理单轮爆量）、回合结束后（只有 codex 提供且默认关闭）、手动触发。手动那条几乎家家都有——用户比任何启发式都清楚「现在该收一收了」。

## 3. 第二问：压成什么

这是分歧最大的一处。压缩的产物直接决定了「丢什么」和「怎么找回」。

**摘要。** 让模型把历史读一遍，写成一份交接单。codex、hermes、pi、learn-claude-code、DSH、Claude Code 都走这条路。
丢的是细节，保的是结论。风险也在这里：摘要说错了，你不会发现——它看起来像事实。所以各家的摘要模板高度趋同，都在反复强调「目标、决策、文件、错误与修复、待办、当前进展」。Claude Code 甚至要求单独一节列出**全部用户消息**，等于给「用户意图不可丢」上保险。

**归档指针。** 不摘要，把原文逐字存到文件里，上下文里只留一句话：「前面 N 条消息已归档，位置在这，需要时去读」。
只有 reasonix 这么做。它的赌注是：**信息不丢，注意力靠自己争取**。代价是模型如果不主动去读，那部分就等于不存在。

**服务端检查点。** 把历史交给服务端，拿回一个不透明的加密块。codex 支持这种模式。
好处是客户端不用理解行为什么；坏处是你失去了所有可见性，而且换一家 provider 就用不了。

**遮蔽。** 历史一个字都不删，只是把某一段标记为「模型不可见」。DSH 是这么做的。
它比归档更彻底：连「搬走」这个动作都没有，正文原地不动，只是投影时跳过。代价是整个会话模型要重写成事件日志，理解成本很高。

**换新窗口。** 不摘要，直接开一个新的上下文，只带走最初的任务设定。codex 提供这个选项。
它把「压缩」这件事简化成「重开」，也就等于承认：留下的价值不如重新说一遍。

五条路，五种不信任的对象：

| 你最怕的 | 该选 |
| --- | --- |
| 模型读到过时信息又照着做 | 换新窗口 |
| 忘了自己为什么这么做 | 摘要（带决策与错误记录） |
| 丢了不该丢的原文 | 归档指针 |
| 连自己丢了什么都不知道 | 遮蔽 + 可观测的边界 |
| 被 provider 绑死 | 都不要，只做本地摘要 |

## 4. 第三问：留多少，按什么单位留

压完之后总得留一段最近的对话——不然模型连「刚才在改哪个文件」都不知道。

三种单位：

- **按 token**：codex、hermes、pi、DSH。精确，但要知道每一段值多少 token。
- **按消息条数**：learn-claude-code（头 3 条 + 尾 46 条）。简单，但一条 `ls` 和一条两千行的文件读取权重相同。
- **按轮次**：reasonix。只保留「当前这一轮」的用户消息，以及这一轮牵涉到的工具调用与结果。

按轮次最不直观，但在工具密集的场景里最稳。原因很朴素：**一次工具调用和它的结果是不可拆的**。按 token 或条数切，很容易切在「调用」和「结果」之间，模型就会看到一个永远等不到返回的调用。所以凡是用 token 预算的，都得额外做一件事——把切点往后挪，直到不切开任何一组调用/结果。按轮次则从模型上避免了这个边界。

还有一条容易被忽略的不变式：**保留量必须小于触发线**。

如果触发线是「窗口减 1.6 万」，而压缩后要保留 2 万 token，那么压完立刻又越过触发线，下一轮再压一次，永远打转，而且每轮都付一次全款。DSH 的做法最狠：这一条在插件加载时就校验，不满足直接报错启动不了。hermes 用三重夹取（比例、窗口占比、触发线占比取最小）达到同样效果。

反过来，pi 的默认配置里保留量（2 万）就大于预留量（1.6 万），而且没有任何校验——在常规窗口下无害，但它把「配置写反了也不会有人发现」当成了可接受风险。

## 5. 第四问：压缩值不值

前面说过，压缩要付一次前缀重建的钱。那么问题就变成：**这一次压缩，值不值得付**。

只有 reasonix 把这个账算清楚了，四条判断：

1. 压完必须真的更小，否则不提交。
2. 常规情况下，压缩后的规模不能超过窗口的一半——不然下一次很快就得再压。
3. 如果固定前缀（系统提示 + 工具说明）本身就超过一半，「压历史」的收益上限很低，这时要求至少省下 25% 才值得做。
4. 第二次压缩要等足够多的新历史累积起来——理由是每次压缩都要付出整份前缀的代价，新增内容太少时净收益为负。

最后一条最容易被忽略，也最值钱。它把「什么时候压缩」从「什么时候快满了」变成了「什么时候攒够了值得付一次钱」。

其他各家在这件事上松得多：DSH 只校验「摘要必须比被遮蔽的内容小」；hermes、pi、codex、learn-claude-code 没有接受条件——压完就算完。

压缩失败之后的态度也分三种，差别很大：

- **降级**：hermes 会退到本地抽取的确定性摘要，不调模型也产出交接单。稳，但要维护两套逻辑。
- **失败关闭**：pi 发现摘要被截断就报错，绝不写入半截；reasonix 归档写不进去就放弃。宁可没压，也不要有错的压缩。
- **什么都不做，但把状态留在原地**：这是最危险的第三种。压缩失败了，可历史没变、锚点也没变，下一轮会以同样的规模再次触发。看起来「什么都没发生」，实际上是「每轮重试一次并付一次钱」。

## 6. 第五问：怎么找回来

压缩之后，模型看到的上下文和磁盘上记录的历史，通常不是一回事。这种差异怎么产生，决定了系统能不能回退、能不能审计、重启后行为会不会变。

两种世界观：

**改写历史。** 压缩后真的用「摘要 + 保留段」替换掉原来的消息列表。简单直接，代价是丢掉的原文只存在于日志里，且运行中的状态和重启后重建的状态是两套代码在算。

**改写视图。** 历史一字不动，每次请求前现算出「这次该让模型看见什么」。压缩只是往状态里记一笔，投影时按这一笔切片。

第二种是主流（pi、reasonix、DSH、codex 都属这一类），但实现难度高得多：你得保证投影的输入是稳定的、可复现的。

由此有一条很实用的判断标准：

> 如果「压缩后模型看见的东西」有两处代码在生成——一处给运行中的会话、一处给重启后的恢复——那它们迟早会不一致。而且不一致的那一刻，不会有任何测试变红，因为两边各自都是对的。

hermes 用一句 SQL 查询解决（模型只读未归档的行，界面两种都读）；reasonix 和 DSH 用同一个纯函数；codex 把压缩结果直接落盘成新的基线。这些都是「单一实现」。

还有第三种更极端的做法：不搬移、不删除，只标记。DSH 把压缩实现成「遮蔽一段区间」，正文原地不动，投影时跳过。好处是恢复、审计、回退全都不受压缩影响；代价是「按索引切历史」的直觉在这里完全失效——多代压缩之后，被遮蔽的区间起点可能比终点还大，因为新摘要落在了旧区间的位置上。

## 7. 回合之内：压缩来不及的时候

前面讲的都是回合之间的事。但一轮里连续二十次工具调用，可以在一次请求之内就把窗口撑爆——压缩根本来不及。

所以每家都有一条「进入上下文时」的防线。手段有五种，按信息损失从小到大：

1. **保留头尾**：超出就截掉中间，留开头（通常是签名、import、结构）和结尾（通常是结果与错误）。
2. **截断**：只留一个方向。读文件保头，跑命令保尾——因为读文件的价值在前半段，命令的价值在后半段。只有 pi 明确区分了这两种。
3. **落盘换指针**：太长就存到文件里，上下文只留路径和一段预览。hermes、reasonix、learn-claude-code、DSH 都这么做。
4. **策略化落盘**：DSH 把这层单独抽成一个包，由策略决定什么时候提示、保留多久。
5. **不落盘，只截断**：codex 是源码可读的六家里唯一这样的。省了磁盘与生命周期管理，代价是模型再也叫不回那部分内容。（Claude Code 是否落盘无法从发行物确认，因此不计入这一条。）

比手段更值得比较的是**留痕**：

- 第一层，什么都不留：模型看到的历史直接从中间开始，而审计侧看不出发生过什么。
- 第二层，说少了多少：「此处省略 N 字节」。知道有损失，但不知道该去哪找。
- 第三层，说去哪找：「完整输出在 <路径>，用 read_file 带 offset 读」。损失可逆。

前两层之间的差别，决定了一个 agent 是「可以调试」还是「只能猜」。

## 8. 那笔看不见的钱：前缀

前面反复提到前缀缓存。这一节说清楚它为什么比压缩更重要。

一条请求可以切成三块：

- **固定前缀**：系统提示、技能目录、工具定义。这一块每次请求都原样重发，是房租。
- **可压缩区**：对话历史。这是压缩的对象。
- **易变区**：当前时间、任务进度、宿主环境。每次都在变。

关键观察：**压缩是偶尔发生的大事，前缀是每轮都在付的日常开销**。你把压缩优化得很好，但每轮都在改系统提示，省下来的钱会从另一个口袋漏掉。

所以成熟实现会做一件事：把易变信息全部赶出固定前缀，放到请求的最末尾。reasonix 把时间、任务进度、宿主上下文全部「每次请求现算、从不写进历史」；DSH 在这条上做到了工程纪律的级别——连「本机路径和端口」都不许进系统提示，同一个事实注册两次，稳定的一半进提示，真实值进运行时上下文。

Claude Code 的观察也印证这一点：它的缓存断点打在**每一条消息的最后一块**上，随着对话滚动前进；这是「让缓存跟着走」的写法，与只打一个固定断点的写法相比，对长会话更友好。

由此可以总结出几条通用纪律，与具体实现无关：

1. 系统提示在会话内不要变。要变就重开一段，或者写进消息里。
2. 技能目录、工具定义这类东西，位置固定、顺序确定。顺序不确定等于每次都换前缀。
3. 时间、进度、环境这类信息，放在请求尾部，不要写进历史。
4. 工具列表的变化是有代价的：新增工具会让它之后的内容全部重算。
5. 压缩是最大的一次断裂，但应该是**少数几次**断裂，而不是每轮一次。
6. 如果拿不出统计，就不要声称缓存有效——多数实现连「这一轮命中多少」都看不到。

## 9. 多个 agent 的时候

上下文不是一个池子。一旦引入子 agent，立刻多出三个问题：

**子 agent 的预算谁负责。** 子会话通常很短，触发不了压缩；于是预算压力全部上移到父层。learn-claude-code 在这件事上有个反例：主 agent 有完整的压缩准备，队友循环却一次都不调用——队友成了整套实现里唯一没有上限的长上下文。

**子结果以什么形态回到父层。** 如果原封不动全文注入，一次大重构的报告可能几万 token，正好把父层挤到压缩线上；更糟的是，下一轮摘要很可能把这份报告压成一句「子 agent 完成了工作」，恰好丢掉后续最需要的东西。

**父层的预算要不要给「工作产物」留位。** 这是一个设计缺口，而不是 bug：多数压缩策略里，一条子 agent 报告和一句闲聊权重相同。codex 用「只保留用户消息」绕开了这个问题，reasonix 用「按轮次钉住当前轮」绕开，而按「最近 N token」保留的实现（包括 Gradus）在这个场景下最吃亏。

## 10. 七家的性格

| | 一句话 | 最值得学的 | 最该警惕的 |
| --- | --- | --- | --- |
| codex | 三条路并存：本地摘要、服务端检查点、换新窗口 | 三种模式共用一套生命周期，可观测性统一 | 只在回合开始压，回合中爆量不做补救 |
| hermes | 把压缩做成运维流程：四阶段、熔断、降级 | 反抖动与确定性降级，生产可用性最高 | 复杂度集中在单点，阈值叠了四层 |
| learn-claude-code | 教学用的成本阶梯：先便宜后贵 | 把「信息损失从小到大」排成可读的顺序 | 字符计量、章节间口径漂移、写放大 |
| pi | 最小正确集：切点合法、可恢复、缓存可复用 | 切点判定与缓存统计重置，两件事都做对了 | 保留量与预留量之间没有校验 |
| reasonix | 用归档代替摘要，把成本写进接受条件 | 「压完值不值」的判断，唯一认真算过的 | 归档不保注意力，模型不主动读就等于丢了 |
| DSH | 插件化 + 事件溯源的遮蔽式压缩 | 前缀纪律成文，保留预算做成加载期断言 | 理解成本高，行为分散在多个插件里 |
| Claude Code | 压得晚（窗口减 13,000），前面有微压缩兜底 | 压缩边界可查（触发方式 + 压缩前 token 数） | 闭源，保留策略与失败处理只能观察不能确认 |

关于 Claude Code 需要说明白：它是闭源产品，上面这些是从公开 npm 包的打包产物里读到的行为（提示词结构、阈值常量、边界消息、缓存断点位置），**不是源码**。能确认的只有「它怎么做」，确认不了「它为什么这么做」「边界情况怎么处理」。所以它在上面这张表里只能算半个样本。

## 11. 如果你要自己做：十二条

不针对哪一家，是这些实现收敛出来的共同点：

1. **先决定你怕什么，再选产物。** 怕丢原文就用归档，怕模型被旧信息带偏就用摘要，怕看不见就加边界记录。
2. **保留量必须小于触发线，并且在启动时校验。** 这条不做，压缩会在小窗口下变成死循环。
3. **切点不能切开工具调用与结果。** 按轮次切最省心，按 token 切就必须补一次对齐。
4. **压缩失败要记账。** 最危险的不是失败，是失败了还保持原状、下一轮再试一次。
5. **摘要请求本身也花钱。** 要么让它复用主前缀（DSH 的做法），要么明确声明它是一次性开销（pi 的做法），不要两头不沾。
6. **可见视图只该有一份生成逻辑。** 运行中一套、恢复时一套，是不一致的标准配方。
7. **工具输出在进入上下文时定形。** 事后再改它，等于每轮都在破前缀。
8. **丢掉的东西要留痕。** 哪怕只是一行「这里少了多少」，也比静默好。
9. **易变信息放请求尾部。** 这是每轮都在省钱的动作，比压缩更划算。
10. **压得晚一点，但要留兜底。** 少压一次就少付一次全款；前提是你有办法在回合内接住爆量。
11. **保留策略至少两个维度。** 只按「最近多少 token」保留，会把用户的约束、关键决策和闲聊同权处理——而那些恰好是检索不出来的信息。加一个「语义角色」维度：约束与决策单独留，普通的工具噪音优先丢。
12. **压缩要留下可查的边界记录。** 触发方式、压缩前后规模、移走了哪一段——这三样写下来，事后才回答得了「它为什么突然忘事」。Claude Code 那条压缩边界消息就是最轻量的做法。
