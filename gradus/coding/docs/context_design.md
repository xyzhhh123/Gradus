# Gradus 上下文管理设计

本文是 Gradus 上下文管理的**目标设计**，不描述当前实现。当前代码只是过渡形态，实现时以本文为准。

改动这一块之前，先看这里的约定，再动代码。

---

## 0. 目标与边界

**要解决**：会话长到装不下时，既能让对话继续，又不让模型突然失忆，也不把记录弄丢。

**不解决**：跨会话记忆、检索增强、多模态理解。

**一句话**：**记录只追加，视图按需算；压缩只改视图，且只在压缩那一刻改。**

## 1. 五条原则

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | 记录不可变 | 会话是一棵只追加的树，任何操作都不修改、不删除已有条目 |
| 2 | 唯一改写点 | 只有「压缩」会改变模型看到的内容，其余时候纯追加 |
| 3 | 单一投影 | 「模型看到什么」只有一个计算入口，运行中与恢复后共用 |
| 4 | 丢弃必留痕 | 任何移出视野的内容，都要在记录里留下可追的痕迹 |
| 5 | 前缀稳定 | 不重排、不中途改写；易变信息放请求末尾 |

原则 2 是地基：守住「唯一改写点」，其余机制可以任意叠加而不互相破坏。

## 2. 数据模型

### 2.1 条目（entry 树）

```
{ "type": "message",  "id": "e12", "parentId": "e11", "message": {...} }
{ "type": "compaction", "id": "c3", "parentId": "e12",
  "summary": "...", "firstKeptEntryId": "e9",
  "tokensBefore": 128000, "trigger": "threshold" }
{ "type": "merge", "id": "m1", "parentId": "c5",
  "text": "...", "supersedes": ["c1", "c3"], "coversFrom": "e2" }
{ "type": "trim", "id": "t1", "parentId": "e20", "dropped": 9, "tokens": 14000 }
{ "type": "usage", "id": "u7", "parentId": "e20", "model": "deepseek-v4.1-flash",
  "input": 18654, "output": 3, "cacheRead": 11136, "cacheWrite": 0 }
```

- 只追加，永不修改删除；
- `parentId` 构成树，支持回退与分叉；
- 压缩/合并记录本身也是条目，因此**只对所在分支生效**；
- `usage` 是**账本记录**：不进消息树、不影响投影，读回时跳过（`SessionFile.load` 显式容忍），
  用来事后算成本与缓存命中。`SessionFile.total_usage()` 把它加总，`Session.usage_totals` 暴露给上层。

### 2.2 活跃叶子

分叉之后「文件末尾」不再等价于「当前叶子」。做法是**追加一条叶子事件**，不改头部、不破坏只追加：

```
{ "type": "leaf", "id": "e20", "parentId": "e2", "leaf": "e2" }
```

- 切换 = 再追加一条；历史一个字不动；
- 后续消息的 `parentId` 指向这条事件，链路因此从目标叶子出发；
- 加载时从最后一行回溯，被放弃的分支自然不可达（仍在文件里）；
- 当前只支持**单个**活跃叶子（见 §12 多分支并行）。

### 2.3 视图（不落盘）

```
视图 = 投影(条目, 活跃叶子)
```

## 3. 投影

### 3.1 定义

```
project(entries, leaf):
    1. 从 leaf 沿 parentId 回溯到根，得到「路径」
    2. 取路径上最近的一条 compaction → 它定义保留起点 firstKeptEntryId
    3. 收集路径上「未被 supersedes 覆盖的」摘要条目，按覆盖起点排序，最多 3 份
    4. 返回：[摘要1][摘要2][摘要3] + 从 firstKeptEntryId 到 leaf 的消息
```

- 没有 compaction → 返回整条路径的消息；
- 摘要消息是临时构造的，不写进记录；
- **沿路径收集**，不是按文件顺序——文件里可能躺着别的分支。

### 3.2 三处调用同一函数

| 场景 | 用途 |
| --- | --- |
| 发请求前（`transform_messages`） | 生成模型可见消息 |
| 会话加载 | 恢复后的初始视图 |
| 压缩时 | 计算「压完还剩多少」 |

### 3.3 硬性要求

**投影必须是纯函数**：同样的条目 + 同样的叶子，结果唯一。不许有隐式状态（缓存、时间、随机）。

## 4. 触发与不变式

### 4.1 阈值

```
预留     = max(16,384, 该模型的 max_output_tokens)
触发线   = 窗口 − 预留
保留量   = min(20,000, 触发线 / 2)
```

两条都要按**当前模型**算，因为不同模型的窗口与输出上限差别很大：

- 预留不能小于一次最大输出，否则「留给输出的空间」比模型一次能生成的上限还小，请求会被自己顶到窗口外；
- 保留量随窗口收缩，避免小窗口下「压完还在线上」。

换模型时必须用新模型的两个值重新校验（窗口变小、输出上限变大都会改变结论）。

### 4.2 启动期断言

```
assert 保留量 < 触发线
```

不满足**拒绝启动**，而不是运行中每轮白花钱。换模型时同样校验一次——新模型的窗口可能更小、输出上限可能更大。

### 4.3 触发时机

| 时机 | 说明 |
| --- | --- |
| 每次请求前 | 主路径 |
| 溢出报错后 | 强制压一次（保留量临时降为 0），仍失败则把错误交给调用方 |
| 手动 | 用户显式要求 |

### 4.4 用量怎么算

```
用量 = 上一次请求的 input_tokens（provider 报的）+ 之后新增内容的估算
```

**锚点绑在「请求」上，不绑在「消息」上。** 压缩后下一次请求会带来新的真实用量，锚点自动更新——不会出现「锚点停在压缩前、下一轮又超线」的死循环。

估算规则：CJK 一字一 token，其余 3.5 字符一 token；图片按固定值折算。

## 5. 压缩事务

一次压缩是一个**事务**，四步顺序执行。任何一步失败都整体放弃，记录不变。

> 早先的版本把「降级」列为第一步，与第四步的「原样重放」互相矛盾：降级会改写要被重放的历史，前缀就不再逐字节一致，缓存收益归零。两者冲突时**优先保缓存**，所以降级并入第三步，只在重放装不下时启用。

**什么时候跑**：轮次**开始前**与**收尾**各检查一次。收尾那次不能省——只在开头检查的话，
本轮新增内容要等下一次请求才进预算，而兜底裁剪那时已经先把旧消息丢了：表面正常，历史在缩水。
（这条是真机上踩出来的，见 `problem.md`。）

### 第一步：算账（不调模型）

- 用当前预算判断是否真的超了触发线（`should_compact`）；没超直接返回；
- 记下压缩前的规模，供第三步的「必须更小」校验用。**两边都用纯估算**：`context_tokens`
  在无锚点时会退回「最后一条带 usage 的 assistant」，那个数描述的是压缩**前**的请求，
  拿来比永远相等，压缩会被一直拒掉。

### 第二步：定边界

```
起点：可见历史里的一个 user 边界
终点：满足全部条件的位置
      - 活跃轮的全部内容都在终点之后（永不切）
      - 工具调用与结果不被拆开
      - 尾部保留量 ≥ 保留量预算
```

实现上靠三条显式检查，而不是「活跃轮总在尾部」的隐含假设（插话、steer 之后那个假设并不成立）：

1. 只在 user 边界切；
2. 尾部保留量 ≥ 保留量预算；
3. **切点不许落进当前轮**（`cut > turn_start` 直接放弃）——当前轮的起点取「最近一条用户自己发的消息」，插话属于本轮的一部分，不能当起点。

**活跃轮超阈值时压缩无效**：若活跃轮本身超过触发线，第 3 条会让切点为空，本次压缩放弃。已实现为**插话提示一次**（`Session._note_turn_too_big`）：「当前这一轮本身太大，没有可折的旧内容；请把任务拆小，或让单次工具输出更短」——否则用户只看到「上下文满了却一直不压缩、只是忘事」。不做无休止重试。

### 第三步：摘要（调一次模型，复用主前缀）

**请求构造**——这是本节的关键，顺序不能变：

```
[与主请求完全相同的工具定义]
[与主请求完全相同的系统提示]
[完整历史，原样重放（不是序列化成文本）]
[最后追加一条用户消息：摘要指令]
```

前两段与历史必须与「上一次真实请求」逐字节相同，否则缓存不命中。缓存断点打在前缀末端（历史最后一条），**不要打在新加的指令上**。

**还有一个容易被忽略的前提：请求头里的会话 id 必须与主对话相同。** 摘要会新建一个 Provider，如果 id 是「一个 Provider 一个」，网关会把摘要路由到另一台没缓存的机器，前缀再像也没用——实测 `cache_read` 从 18,560 掉到 0。所以 `{run}` 在**会话创建时**就固化（`Session.connect`），主对话、摘要、合并共用同一个 id。

**摘要指令要求**：

- 固定 8 栏，缺项写 `(none)`：目标与意图 / 约束与偏好 / 已完成的工作 / 当前状态 / 关键决策与理由 / 错误与修复 / 待办 / 关键文件与位置；
- 路径、命令、报错原文、标识符、数字原样保留；
- 不许改用户原话；
- 明确写「不要继续对话、不要调用工具、只输出摘要」。

**兜底一：模型想调工具** → 丢弃本次结果，按失败处理（`CompactionError`）。

**兜底二：重放装不下**（请求本身超窗）→ 退回「先降级、再拍成文本、另起请求」。降级三招都做了：工具结果截断到 2,000 字符、**相同工具结果去重**（按内容哈希，重复的只留「与第 N 条相同」）、**助手正文压成一行**（保留开头 200 字 + 原长度）。实测一段 28,389 字符的历史拍平后 4,587 字符（少 84%）。用户原话不动，工具调用的名字与参数保留。这一次没有缓存可复用，但省窗口。

**提交前校验**：摘要后的视图必须比压缩前小，否则放弃。比较用**纯估算**：`context_tokens` 在无锚点时会退回「最后一条带 usage 的 assistant」，它描述的是压缩**前**那次请求，两边相等，压缩会被永远拒掉（真机踩过，见 `problem.md`）。

**失败处理**：失败关闭（不写半截）；按 **1 / 2 / 4 / 8 轮**退避后再试（`COMPACT_RETRY_SKIPS`），成功即清零——记一次计数、此后若干轮不再自动尝试，避免端点持续报错时每轮重付一次注定失败的摘要请求。

> 不做「本地降级摘要」：维护两套摘要逻辑的成本远高于收益。

### 第四步：提交

追加一条 compaction 条目（见 §2.1）。**历史本身一行不改。** 下一次请求的视图就变成「摘要链 + 保留段」。

### 5.1 分层摘要与合并

**分层**：每次压缩产生一份新摘要，**不重写旧的**。这样近期内容永远保真，不会陷入「摘要的摘要」。

**上限**：视图里最多 3 份摘要，合计不超过约 1,500 token。

**合并**：超过上限时，把**最旧的两份**合并成一份，写成一条 `merge` 条目：

```
{ "type": "merge", "text": "<合并后的摘要>",
  "supersedes": ["c1", "c3"], "coversFrom": "e2" }
```

- 字节只追加，原摘要条目保留；
- 投影时被 `supersedes` 覆盖的摘要不再参与；
- 排序键用被合并摘要中最早那份的覆盖起点。

**效果**：退化只发生在最老的边缘，近期摘要从不被重写；总量始终有界。

**合并失败**：保持原样，下次再试，不写半截。

### 5.2 已知退化：裁剪先于压缩时，摘要缓存会归零

**结论先说**：不影响正确性，只影响**那一次摘要的价钱**。已实现、**未修**，记在这里免得下次重新发现。

**时序问题**：

| 顺序 | 谁在动作 | 后果 |
| --- | --- | --- |
| 请求发出前 | `transform_messages` 里的 `plan_trim` | 视图超线时**先把旧消息裁掉**，这一发实际发出去的是裁过的版本 |
| 轮次结束后 | `_maybe_compact` | 这时才压缩，重放的是**完整投影** |

两边开头不一致 → 服务端前缀缓存匹配不上 → 那一次摘要的输入按全价计。**只要某一发被裁过，紧随其后的摘要必然归零。**

**什么时候会踩到**：把窗口压小、或某一轮突然爆量（一次读几个大文件）时必然；正常配置（窗口远大于触发线）下压缩先生效，很少踩。

**怎么观测**：`Session.last_summary_usage` 记着每次摘要请求的用量。命中时 `cache_read` 约等于上一发请求的输入长度；归零时它是 0，且 `input_tokens` 明显大于上一发。真机脚本 `verify_context_live.py` 已就这条做断言。

**修法草案（未做）**：把压缩提到裁剪**之前**——`transform_messages` 里发现 `plan_trim` 要丢消息时，先 `await` 一次压缩再重新投影。这样摘要的前缀正好是上一发真实请求的原文，能吃满缓存；顺带消掉「压缩晚一步、历史先被裁」这个同源问题。代价是钩子要多一条通往会话的回调、并处理重入（压缩自己也会发请求）；轮末那次保留作兜底。

> 召回（`recall_history`：按 id 或关键词把折叠掉的原文取回）的完整说明见 [recall.md](recall.md)。

> 会话 id 是另一个坑，已修：`{run}` 曾按 Provider 实例生成，摘要换了 id 被网关路由到没缓存的机器，`cache_read` 从 18,560 掉到 0。现在在会话创建时固化，见 `problem.md`。

## 6. 保留策略

只有一个维度：**轮次**。

```
保留 = max(活跃轮的全部内容, 尾部 token 预算)
```

- 活跃轮：从最近一条用户消息开始到当前为止的全部内容（含其工具调用与结果）；
- 其余：从尾部往前累加到预算为止；
- 更早的：进入摘要。

**不要**引入「永久保留某类消息」——那会让旧内容长期占位。语义重要性由摘要栏目保证。

## 7. 检索

### 7.1 工具

```
recall(ids=["e42"] | query="retryWithBackoff", limit=8)
```

- 按 ids：读回指定条目的原文；
- 按关键词：在**已压缩区段**内按出现次数排序，返回 `#e42` + 片段。

### 7.2 三条约束

1. **只检索已压缩的部分**。还在上下文里的 id 会被拒绝，并提示直接看上下文——
   否则等于为同一条信息付两次钱；
2. **地址是条目 id，不是序号**：回退/截断之后下标会指向别的消息，id 不会；
   没有会话文件的内存会话按位置合成 `e1..eN`，只追加时同样稳定；
3. **有预算**：每代上限窗口的 10%（下限 2,000 token），超了**整段拒绝**，不截断。

### 7.3 为什么必须有

摘要必然丢细节。没有找回入口，丢掉的就是永久丢失。

## 8. 单轮兜底

### 8.1 工具输出在进入上下文时定形

超过上限就**落盘换指针**：

```
① 完整内容写入文件（会话目录下的 outputs/）
② 上下文里只留：路径 + 预览（前若干行）
③ 条目里记相对路径
```

- 日志永久，落盘文件**按引用计数**清理：只要还有条目引用它，就不删；
- 会话删除时统一清理。

### 8.2 请求前硬裁必须留痕

- 注入一条标记消息：「已移除 N 条早期消息，约 M token」；
- 同时在记录里追加 `{"type":"trim","dropped":N,"tokens":M}`。

**静默丢弃是最坏的设计**：出事时连「它为什么忘事」都答不上。

## 9. 缓存纪律

| 规则 | 理由 |
| --- | --- |
| 历史只追加，不重排 | 前缀变了就全量重算 |
| 易变信息（时间、进度、环境）放请求末尾 | 它们每轮都变，不能进前缀 |
| 系统提示会话内不变 | 变则整段重算 |
| 工具列表只追加，不插入 | 新工具插中间会让后面全部失效 |
| 摘要请求复用主前缀 | 工具定义 + 系统提示 + 历史原样重放，只追加一条指令 |
| 摘要断点打在前缀末端 | 打在新增指令上等于写一份永不复用的缓存 |
| 摘要必须用同一个模型 | 缓存按模型存，换模型不命中 |
| 命中率必须可见 | 没有观测，前面所有规则都是空话 |

**换分支的代价是「分叉点之后重算」，不是全量重建。**

前缀缓存认的是最长公共前缀：两条分支在分叉点之前的历史逐字节相同，那一段照常命中。

| 情况 | 失效起点 |
| --- | --- |
| 没压缩过，或压缩发生在分叉**之前** | 分叉点 |
| 压缩发生在分叉**之后** | 视图第一条（两条分支的摘要不同，公共祖先被挡住） |

举个量级：公共祖先 100K、新分支尾巴 5K，切换成本约 `100K × 1/10 + 5K ≈ 15K`，而不是 105K。

## 10. 多 agent

- 子 agent 的结果进入父会话时**带身份标记**（`Bus.render` 的 `<message from=...>`）；
- 压缩选边界时，**最近几条子结果所在的那一轮不进入被摘要的区段**——摘要按 token 说话，不区分闲聊和成果；
- 不给子结果单独做摘要——那是另一套机制，收益不成比例。

## 10.1 分支切换不影响磁盘

`switch_branch` 只回退**对话**：历史与视图切到另一条链，但工作区里的文件已经改过了，不会跟着回退。

这是回退功能的固有性质（归档式上下文也一样）：上下文可以时间旅行，磁盘不行。将来做「改历史重试」时必须显式提示这一点，否则用户会以为代码也回去了。

## 11. 分层归属

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| `ai` | 用量上报、provider 适配、缓存断点控制 | 任何策略 |
| `agent` | Message 结构、纯函数（估算 token、找切点）、投影的调用点 | 压缩决策、摘要、持久化 |
| `coding` | 条目读写、投影实现、触发策略、摘要、recall、落盘 | provider 细节 |

**纯函数可以下沉到 `agent`；凡是涉及「何时、是否、存哪」的判断，一律留在 `coding`。**

## 12. 明确不做的事

| 不做 | 理由 |
| --- | --- |
| 归档文件（导出副本） | 条目本身就是文件，再导一份会造成跨代重复 |
| 事件溯源重构 | 收益不足以抵消改造整个会话模型的成本 |
| 插件化压缩策略 | 只有一套策略，抽象层是负担 |
| 服务端检查点 | 绑定特定 provider |
| 每轮降级 | 每轮改写 = 缓存每轮归零 |
| 本地降级摘要 | 两套摘要逻辑的维护成本高于收益 |
| 向量检索 | 关键词 + 词频排序已够用，向量引入额外依赖 |
| 多分支并行 | 每条分支要独立预算与配额，成本翻倍；`activeLeaf` 字段保留扩展空间 |

## 13. 落地顺序

| 批次 | 内容 | 验收标准 |
| --- | --- | --- |
| 一 | 启动断言、锚点改为「按请求」、丢弃留痕 | 小窗口不再反复压缩；会话文件能查到丢弃记录 |
| 二 | 条目/投影分离 | 运行中与重启后视图逐字节一致（已有测试固定 `test_runtime_view_matches_restored_view`） |
| 三 | 压缩事务五步 + 摘要复用前缀 | 四步顺序执行（算账 → 定边界 → 摘要 → 提交），**降级改成兜底**不再单独成步；摘要复用主前缀；工具调用即判失败；失败按 1/2/4/8 轮退避；活跃轮超线时提示一次 |
| 四 | 分层摘要与合并；recall；落盘；子结果标记 | 四代压缩后总量有界；压缩后可取回原文；超大输出可追 |

## 14. 可调参数

| 参数 | 默认 | 配置项 | 何时调整 |
| --- | --- | --- | --- |
| 窗口（预算口径） | 模型能力，查不到时 128,000 | `context_window` / `GRADUS_CONTEXT_WINDOW` | 想省成本 → 往下压；超过能力会被收敛 |
| 窗口（能力上限） | 端点元数据 > 实测静态表 | `probe_limits` / `GRADUS_PROBE_LIMITS`（默认关） | 端点不报 limit、表里又没有时打开探测 |
| 输出上限 | 8,192（能力上限单独记在 `output_limit`） | `max_output_tokens` / `GRADUS_MAX_OUTPUT_TOKENS` | 模型支持很长输出且确实需要时 |
| 预留守 token | 16,384（且不小于该模型 `max_output_tokens`） | `context_reserve_tokens` / `GRADUS_CONTEXT_RESERVE` | 模型输出上限变化大时 |
| 保留量 | 触发线 × 25%（下限 12k、上限 64k） | `keep_preset` / `GRADUS_KEEP_PRESET`（`conservative` / `balanced` / `aggressive`） | 想少压几次 → `aggressive`；想压得更狠省钱 → `conservative` |
| 保留量（精确值） | — | `context_keep_tokens` / `GRADUS_CONTEXT_KEEP` | 有明确目标值时才用，优先于预设 |
| 摘要份数上限 | 3 | `summary_layers` / `GRADUS_SUMMARY_LAYERS` | 长会话多 → 调大（但每份都占上下文） |
| 摘要总量上限 | ~1,500 token | `summary_tokens` / `GRADUS_SUMMARY_TOKENS` | 同上；份数没超但每份都长时靠它兜底 |
| 检索预算 | 窗口 10%（下限 2,000） | `recall_tokens` / `GRADUS_RECALL_TOKENS` | 检索频繁但命中率低 → 调小 |
| 零命中选择器 | 开 | `selector` / `GRADUS_SELECTOR` | 想省掉「零命中时那一发小请求」就关掉；关掉后只剩关键词检索与目录兜底 |
| 落盘阈值 | 单条 30,000 字符（命令）/ 30,000（`codemode`） | `tool_output_chars` / `GRADUS_OUTPUT_CHARS` | 按模型窗口与工具习惯调 |

上限类的语义是「不填走推导，填了必须为正整数」：`None` 与 `0` 不同——`0` 直接报错，
不会悄悄退回默认值。窗口与输出上限还多一条：**空串也算填错**（多半是笔误）。

**不可配置的三条**（写死在 `context.ContextBudget` 里）：

- 保留量必须**严格小于**触发线——显式配了过大的值直接报错，不悄悄改小；
- 保留量不超过**触发线的一半**——保证压完确实明显变小，不会刚压完又触发；
- 预留不小于 `max_output_tokens`——否则请求会被自己的输出顶到窗口外。

### 15.2 验证顺手挖出的沙箱 bug（已修）

第一次跑真机脚本时 `restricted` 后端起不来，报
`ACL AddAccessRule failed on <dir> (exit 1)`，stderr 被吞掉了。把 stderr 捞出来，
是三个叠加的坑，都在沙箱层，与上下文逻辑无关：

| 坑 | 现象 | 原因 | 修法 |
| --- | --- | --- | --- |
| 用 `Get-Acl` | `the module could not be loaded` | 子进程是 Windows PowerShell 5.1，却继承了 pwsh 父进程的 `PSModulePath`（PS7 目录），5.1 解析到 PS7 的模块就废了 | 脚本不再调 cmdlet |
| 用 `Set-Acl` | `does not possess the 'SeSecurityPrivilege'` | 非提权令牌在**受保护 DACL** 的目录上改 ACL 要特权；`tempfile.mkdtemp` 造出来的目录正是受保护的（SDDL 带 `D:P`），而 scratch 就是它造的 | 改走 `DirectoryInfo.GetAccessControl()` / `SetAccessControl()`（Win32 `SetSecurityInfo`，只要 `WRITE_DAC`） |
| 用 `mkdtemp` 建 scratch | `codemode` 报 `script exited without a result` | 同上那个受保护 DACL：只授 `OWNER RIGHTS`，而受限令牌是 LUA 过滤令牌，匹配不上，子进程读不到 scratch 里的脚本 | Windows 上改用普通 `mkdir`（`sandbox._private_dir`），POSIX 保持 `mkdtemp` 的 0700 |

所以 `_ACL_SCRIPT` 现在整段只用 .NET 类型；副作用是 `icacls *SID` 那条路确实不行
（`No mapping between account names and security IDs`），合成 SID 只能这样加。
`_legacy_module_env()` 仍给 5.1 子进程一份自己的模块路径，作为以后在里面加 cmdlet
的保险。修完后契约测试（`GRADUS_SANDBOX_LIVE=1`）11 passed / 1 skipped。
