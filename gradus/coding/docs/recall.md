# 召回（recall）：把压缩掉的历史取回来

> 配套阅读：[context_design.md](context_design.md)（压缩与投影）、[design.md](design.md) §5.9（工具面与检索）。
> 相关代码：`coding/history.py`（渲染与读取）、`coding/tools/recall_history.py`（适配器）、`coding/retrieval.py`（分词与 BM25）、
> `coding/selector.py`（零命中的小窗口兜底）。

## 1. 它解决什么问题

压缩是**有损**的：一份摘要固定八栏、总量约 1,500 token，要把几十轮对话压进去，细节必然丢——
报错原文、具体路径、某个数字、当初为什么这么改。

丢了会怎样：模型开始**重复劳动**——重新读那个文件、重新问同样的问题，或者忘了当初把重试次数
改成 5 的理由。

`recall_history` 就是那个"按需把原文取回来"的入口。它成立的前提是我们选择了**记录与投影分离**：

```
历史记录（只追加，一行不改）
   │
   ├── project_view 投影 ──→ 模型看到的视图 = 摘要 + 保留段
   │                              ↑ 被折叠的那段（first_kept 之前）模型看不见了
   │
   └── recall ───────────────────┘ 但记录里还在，可以按 id 或关键词取回
```

如果压缩是"删掉旧消息"，`recall_history` 根本无从存在。正因为压缩只是"把内容移出视野"，
它才有可能从"不可逆的销毁"变成"可逆的移出"。

## 2. 两条路径

| 路径 | 参数 | 返回 | 精确性 |
| --- | --- | --- | --- |
| 按 id | `ids=["e42"]` | 该条目的**完整原文**（逐字，不摘要） | 精确：id 是稳定标识 |
| 按关键词 | `query="重试次数"` | 命中条目的**片段**（240 字符窗口） | 概率性：靠分词与打分 |

两条路径互斥（同时给会被拒绝），最多 20 条（`MAX_LIMIT`），默认 8 条。

**可见性规则**：只能读 `first_kept` 之前的部分。还在上下文里的条目会被拒绝
（"直接读上下文即可"）——没必要为看得见的东西花一次工具调用。

**返回顺序**：按 id 时按**你给的顺序**；按关键词时按**分数**从高到低，同分按历史位置。
都不是"按历史顺序整段搬过来"。

## 3. 预算：每代压缩一份

`recall_history` 不是无限回读。每**一代**压缩（`CompactionState.version` 变化）有一份配额：
窗口的 10%，下限 2,000 token（`recall_tokens` / `GRADUS_RECALL_TOKENS`）。超了整段拒绝：

```
recall: 需要 8,400 token，本代只剩 3,100；请缩小范围
```

理由很直接：允许无限回读，模型会把刚压下去的内容原样倒回来，压缩等于白做。

## 4. 关键词检索怎么工作

```
查询 ── tokenize ──→ 规范词 ── BM25 ──→ 位置排序 ──→ 取片段 ──→ 工具结果
```

### 4.1 分词（`retrieval.tokenize`）

| 步骤 | 作用 | 例子 |
| --- | --- | --- |
| 拆驼峰与下划线 | 让 `retryWithBackoff` 能被 `retry`/`backoff` 命中 | `retryWithBackoff` → `retry`, `with`, `backoff` |
| 去停用词 | "the/type/string/tool" 这类词在每条描述里都有，留着只会把分数拉平 | — |
| 简单词干化 | 复数归并 | `issues` → `issue` |
| **中文 2-gram** | 中文没有空格，整句会变成一个 token | 「标记任务完成」→ 标记/记任/任务/务完/完成 |
| **双语同义词** | 历史里大量是英文标识符，中文查询要靠它落地 | 「重试」→ `retry`、「子代理」→ `agent` |

后两步是**偏离 Pi** 的地方：Pi 的分词器只认 `[a-z0-9]`，中文查询在那边必然零命中。

### 4.2 打分（`retrieval.bm25`）

Okapi BM25，k1=1.2、b=0.75，与 Pi 一致。检索文档是**被折叠消息的正文**
（`tool_search` 用的是工具元数据，两边共用同一套分词与打分，文档构造不同）。

### 4.3 片段定位：一个真实踩过的坑

返回的不是整条消息，而是 240 字符的片段，需要先在原文里找到命中处。最初的实现用的是
**映射后的词**：

```python
anchor = min(lowered.find(term) for term in terms if term in lowered)  # terms 里有 'retry'
```

查询「重试」→ `terms` 是 `['retry', ...]` → 中文原文里找不到 `retry` → `default=0` → **片段从开头截**。
结果是：条目找对了，给你看的是开头那段废话，命中处在 400 字符之外。

修法：定位用**原文字面词**（`retrieval.surface_terms`：只做 2-gram 与英文小写，不做映射），
打分仍用映射后的词。测试断言目标句必须落在返回文本前 200 字符内。

### 4.4 分词缓存

已压缩的消息只追加、内容不变，所以分好的词可以缓存：
键是 `(条目 id, 正文长度)`，`Session._recall_tokens` 持有。区段几万字符时首次几十毫秒，
之后基本零成本。

## 5. 兜底链

```
关键词命中 ──→ 直接返回片段
   │
   └─ 零命中 ──→ 小窗口选择器（selector.py，默认开）
                    │ 给它「候选清单（id + 前 80 字，封顶 30 条）+ 查询」
                    │ 它回 {"ids": [...]}（最多 4 条）
                    │
                    ├─ 挑到了 ──→ 走按 id 读取
                    └─ 没挑到 ──→ "没有命中…"
```

**为什么要有选择器**：关键词是字面匹配，同义词表覆盖不到的说法会落空。选择器是一个独立的小
请求——它不读主对话、不带工具、不共享前缀缓存。

| 项 | 值 |
| --- | --- |
| 触发 | 只在零命中时；命中时一次都不调 |
| 次数 | 一次 `recall_history` 最多一发，不递归 |
| 成本 | 输入约 300 token、输出 50–250 token（主对话一轮是 18,000+） |
| 参数 | `max_output_tokens=600`、`temperature=0`、`MAX_PICKS=4` |
| 失败 | 解析失败/超时/异常一律返回空结果，不抛给调用方 |
| 开关 | `selector` / `GRADUS_SELECTOR` |

实测（8 条历史、5 条查询）：**5/5 挑对**。典型例子「别引额外的中间件」→「缓存层用进程内 LRU」
（关键词零命中）；「刚才测试跑得怎么样」→ 关键词误命中 e4，选择器给了 e5。

## 6. 已知限制

| 限制 | 说明 |
| --- | --- |
| 只在零命中时触发 | 「命中但答错」不介入。改成置信度阈值需要先积累打分分布的数据 |
| 同义词表要人维护 | 覆盖不到的说法会落空，选择器兜住；表再加只会"少一轮" |
| 片段 240 字符 | 命中处前后的内容可能被截断；需要全文时应当用 id 路径 |
| 预算拒绝即失败 | 一次要得太多会整段拒绝，模型需要自己缩小范围（错误信息里给了剩余量） |
| 同一个模型当裁判 | 选择器质量取决于当前模型；可以配便宜的小模型专门做，属未定 |

## 7. 结构

| 文件 | 内容 |
| --- | --- |
| `coding/history.py` | `RecallError` / `render` / `read_ids` / `search_positions` / `render_hits` / `search` / `candidates` / `search_with_selector` |
| `coding/tools/recall_history.py` | `RECALL_HISTORY_SPEC` / `RecallHooks` / `RecallHistoryTool`（只做参数转换） |
| `coding/retrieval.py` | 分词与 BM25（与 `tool_search` 共用） |
| `coding/selector.py` | 零命中的小窗口兜底 |

工具名从 `recall` 改成 `recall_history`：`recall` 在检索语境里容易被读成"召回（recall@k）"，
其实是"把压缩掉的历史取回来"。纯逻辑本来和适配器挤在 `tools/recall.py` 里，`session.py` 反向
依赖工具模块；现在逻辑在 `coding/` 顶层，`tools/` 只放适配器。

未做：把选择器兜底也接给 `tool_search`。

## 8. 一句话

- `tool_search` 解决「**我有哪些能力**」；
- `recall_history` 解决「**我之前干了什么、为什么这么干**」；
- 两者共用 `retrieval.py` 的分词与打分，但池子、预算、返回形态完全不同，所以是**两个工具**。
