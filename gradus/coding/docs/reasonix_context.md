# Reasonix 上下文管理：设计思路

本文只讲**结构**和**为什么这么设计**，不逐行讲代码。
想核对实现时看最后一节的入口表。

## 术语表

先统一几个词，后面不再解释。前三个是角色，后五个是动作和状态。

| 词 | 代码里叫什么 | 一句话 |
| --- | --- | --- |
| 记录 | canonical / transcript | 会话的完整原始日志，只追加，永不修改 |
| 检查点 | projection | 一份"替身"：说明前面哪一段已经移出上下文，以及归档文件在哪 |
| 呈现 | view | 这一轮真正发给模型的消息，每次请求现拼 |
| **折叠** | fold | 把一段历史**移出上下文**：原文写进归档文件，原地换一句指针 |
| 归档 | archive | 折叠写出来的那个文件，内容是逐字原文 |
| 指针 / 便条 | archive pointer | 折叠后留在对话里的那条消息，写着归档文件的路径和怎么读 |
| 闭合 | closed | 一次工具调用已经拿到结果；没拿到就叫"未闭合" |
| 尾巴 | tail / derived tail | 拼在请求最末尾、每轮现算、不写进历史的内容 |

**折叠**就是本文唯一的核心动作。后面所有"移出上下文"说的都是它。

---

## 一、它面对的问题

窗口是有限的，会话是无限的。窗口满了以后，只有三种选择：

| 做法 | 本质 | 代价 |
| --- | --- | --- |
| **丢**（截断） | 把旧内容删掉 | 信息永久消失 |
| **压**（摘要） | 用一段短文字替换旧内容 | 判断在"还不知道下一步要什么"时做出，且不可撤销 |
| **搬**（归档） | 把旧内容挪出上下文，留在磁盘上 | 模型需要时得自己回去读 |

大多数 harness 是"先丢、再压"。
Reasonix 选的是**搬**，并且围绕"搬"把整个系统重新排了一遍。

这个选择决定了后面所有设计：既然信息还在，就不需要在压缩时做取舍；
既然不需要取舍，压缩就可以做得**很笨、很粗暴、很安全**。

## 二、一句话结构

用大白话说，整个系统就做三件事：

1. 会话有一份**只增不改的原始日志**；
2. 窗口紧张时，把前面一大段原文**抄到一个文件里**，日志里那一段换成一句"东西在哪儿"；
3. 每次请求前，用这份日志**现拼**出发给模型的消息。

这三个动作对应三个角色：

```
记录（canonical）
  完整对话，只追加，永不修改。
  它不参与"这轮发给模型什么"的计算，只负责"事实还在"。

检查点（projection）
  一个可以被整体替换的"替身"。
  内容 = 稳定头 + 一条归档指针 + 少量保留内容。
  它只描述"前面那一段已经被移出上下文了"，不描述"前面那一段说了什么"。

呈现（view）
  这一轮真正发给模型的消息。
  = 检查点 + 记录里尚未被检查点覆盖的部分 + 几条现算的尾巴。
  每轮现拼，不落盘。
```

三层的职责是**分开的**：

- 记录负责**不丢**；
- 检查点负责**变短**；
- 呈现负责**这一轮该看什么**。

关键在于：**"变短"只动检查点，不动记录**。
所以压缩不再是"销毁信息"，只是"换一副眼镜"。
眼镜换错了可以摘掉，记录还在。

### 2.1 "归档"具体是什么

**把一段对话的原文抄进一个文件，然后在对话里留一句话告诉模型文件在哪。**

它和"摘要"的区别只有一点：摘要会重写内容，归档只是搬家。

举个具体的。折叠前，模型看到的历史大致是：

```
[system]     你是一个 coding agent……
[user]       把登录改成 JWT
[assistant]  先看下现有实现
             → read_file(auth.py)
[tool]       1→def login(user, pwd): ...
[assistant]  改成签发 JWT
             → edit_file(auth.py, ...)
[tool]       ok
[user]       再加个刷新 token
```

折叠后，中间那一大段被换成一句话：

```
[system]     你是一个 coding agent……
[user]       <compaction-summary>
             47 earlier message(s) were moved out of this conversation…
             Archive: …/sessions/xxx/fold-3f9a2c.md
             Read it with read_file … Do not guess what it contains.
             </compaction-summary>
[user]       再加个刷新 token
```

而被移走的内容，原封不动躺在那个文件里：

```
[user]
把登录改成 JWT

[assistant]
先看下现有实现
[assistant calls read_file] {"path":"auth.py"}

[tool read_file result]
1→def login(user, pwd): ...
...
```

模型需要时用 `read_file` 分段读，或者用 `grep` 搜。
文件按内容哈希命名，同一段折叠两次会得到同一个文件，不会重复占盘。

## 三、为什么这么拆：一切都从缓存倒推

模型侧的 prompt 缓存，命中规则只有一条：

> **从第一个 token 开始，连续相同的前缀才算命中。**

这意味着：

- 会话一直往后追加 → 前缀不动 → 命中率很高；
- 一旦改了历史里的某个字节 → **从那个字节起全部失效**，后面全部重算。

"从那个字节起"是字面意思：system prompt 本身没变，所以最前面那一段仍然命中。
折叠是从 system 之后开始替换的，所以**断开点就在 system 的末尾**，后面整段失效。
system 通常只有几千 token，对话有十几万，所以成本上几乎等同于整段重算。

这里有个反直觉的推论：既然断开点已经在 system 末尾，那"一次折叠移走多少"在缓存代价上没有区别——
断都断了，后面无论留多少都是未命中。所以它的选择是"能移走多少移走多少"，
而不是"少移一点、保住更多缓存"。

所以上下文管理真正的成本，不是"多存了多少 token"，而是**"改写了几次历史"**。

Reasonix 的全部设计可以浓缩成两条纪律：

1. **平时绝不改写历史。** 低于阈值时，一个字都不动——不摘要、不裁剪、不递增版本。
2. **必须改写时，只改一次，且把改动集中在最前面。** 折叠是一次性的、整体替换的、罕见的事件。

由此还能推出第三条，也是它最有辨识度的一条：

3. **所有易变的东西都放到请求的最末尾。**

因为缓存只认前缀，末尾怎么变都不影响命中。
于是任务状态、进度记录、宿主上下文这些东西，全都做成"每轮现算、追加在最后、从不进历史"的尾巴。

## 四、走一遍：一次折叠到底发生了什么

假设窗口 200K，阈值 90% → 触发线 180K。

**第 1–20 轮**：一路追加。什么都没发生，前缀一直没变，命中率很高。

**第 21 轮**：估算到 182K，越过触发线。开始一次折叠：

1. **决定折哪一段**
   从 system 之后开始，一直折到"最后一个工具调用已经有结果"的位置为止。
   如果当前轮已经跑了一半，这个终点会落在当前轮内部——
   所以折叠区不是"当前轮之前"，而是"到最后一个闭合点为止"。
   为什么是这个边界：再往后可能有一个"发了调用、还没收到结果"的回合，
   把它一起移出上下文，模型会看到一个永远等不到回应的调用，provider 直接报错。

2. **决定留什么**
   保留名单里只有**当前这一轮的那条用户消息**。
   还没拿到结果的工具调用本来就在折叠边界之外，会作为"尾巴"实时拼回。
   已经拿到结果的工具调用和输出会随这一段一起归档——归档是逐字的，需要时可以回读。
   别的历史全都可以移走，包括上一轮的用户消息。
   注意：它**不是**"保留最近 2 万 token"，而是"按轮判定谁不能动"。保留的单位是**轮**。

3. **写归档文件**
   把要折的那一段原样写成 `fold-<内容哈希>.md`，放在会话旁边。
   **不摘要、不压缩、不改写**，逐字保存。

4. **原地留一张便条**
   上下文里那一段被替换成一段话，大意是：
   > 前面 N 条消息已经搬到 `<路径>` 了，没有摘要，记录是完整逐字的。
   > 需要的时候用 read_file 分段读，或者用 grep 搜。别猜它写了什么。

5. **验收**
   新的呈现必须满足三个条件才允许装上：比原来小、低于触发线、正常情况不超过窗口的一半。
   **不够小就不装**，宁可继续顶着阈值跑，也不装一个"看起来压过但其实没省"的检查点。

6. **落账**
   记下这次折叠覆盖到记录的哪个位置、那一段的指纹、以及"这次确实打碎了缓存"。

结果：182K 掉到大概 20K–60K（典型落点是窗口的 10%–30%）。
模型下一轮看到的是：system + 那张便条 + 当前轮 + 几条尾巴。

折叠后剩多少，只取决于三样东西：**system prompt、那张便条、当前这一轮**。
那 180K 里绝大部分是"已经干完的轮次"，所以一次折叠就掉得这么多。
反过来说，如果当前这一轮本身就很大（比如已经读了十个文件），折叠后就不会这么小——
它不会为了压到某个数字而把正在干的活移出上下文。

它敢一次移走这么多，是因为**归档不丢信息**：被移走的内容逐字躺在文件里，模型随时能回去读。
移走得多只是把"要不要读"的决定交给模型，不是把内容删掉。

**第 22–40 轮**：继续追加，前缀稳定，命中率恢复。

**第 41 轮**：又到阈值。但这次不会立刻折叠，而是先算一笔账。

先看清一件事：**第二次折叠并不能多移走"已经移走的东西"。**
第一次折叠之后，前面的历史已经变成一张便条了；再折叠一次，那张便条还是那张便条，
一个新字节都不会多移走。第二次折叠真正能新移走的，只有
"上次折叠边界之后新长出来、且已经干完的那一段"。

这段东西就叫**新增的闭合历史**：

- **新增**：在上一次折叠的边界之后；
- **闭合**：工具调用都已经拿到结果，而且不属于当前还在跑的这一轮。

然后算账。折叠本身几乎不花钱（归档不调模型），贵的地方是**它把 system 之后的内容整体换掉了**：

| | 不折 | 折 |
| --- | --- | --- |
| 下一轮 | 约 180K，绝大部分是**缓存命中**，很便宜 | 约 30K，但从 system 之后**全部未命中**，按原价重算 |
| 之后每轮 | 多带 S 个 token（按命中价，很便宜） | 少带 S 个 token |

所以折叠的收益是"**之后每轮省一点点**"，成本是"**这一轮整段重算一次**"。

S 越小，回本越慢：移走 2K，可能要几十上百轮才抵回来；移走 32K，几轮就抵回来。
会话如果没那么多轮，这次折叠就是净亏。

这就是门槛看"**新增**了多少"、而不是"现在总共多少"的原因——
总量再大，也早就被上一次折叠移走了，再折叠一次不会多省一个字节。

换个类比：旧货搬到隔壁仓，搬运本身免费，但换门牌会让快递系统把整个仓库重新扫描一遍。
扫描费是固定的，之后省下的是"少搬那点货"的运费。货太少，扫描费都赚不回来。

## 五、这几条规则，以及为什么是它们

下面五条不是五个独立开关，而是上面那套结构自然推出来的结论。
只要接受"记录只追加、呈现现拼、折叠是罕见事件"，这五条基本是必然的。

**一、移走的内容不做摘要。**
折叠时它不去总结这段对话，只是把原文抄到文件里。
摘要当然也是模型写的，但写摘要的那次调用和继续干活的那次调用，处境完全不同：
它只看得到被移走的那一段，看不到接下来要做什么；
它必须现在就把"什么重要"定下来，而原文马上会被替换，定错了也补不回来。
也就是说，摘要是在**信息更少、时机更早、且不可撤销**的条件下做的判断。
归档不做这个判断，把"要不要读、读哪一段"推迟到真正需要的那一刻——
那时继续干活的模型已经知道自己在找什么，而且只读需要的那一小段就够。
这条规则有个前提：工具集里必须有可靠的文件读取和搜索，否则归档等于把信息扔掉。

**二、保留的是"这一轮"，不是一个 token 数。**
折叠的保留名单里只有当前轮的那条用户消息；还没拿到结果的调用在折叠边界之外，会作为尾巴拼回。
其他历史全都可以移走，包括上一轮的用户消息，以及本轮已经拿到结果的工具调用。
（代码里 `agent.go` 的字段注释写的是"保留这条消息及其之后全部逐字"，与 `keepIndexes` 只标记
用户消息的实现不完全一致；这里按实现写。）
用 token 数卡不合理，因为一轮可能只有一句话，也可能有二十次工具调用；
卡小了会把正在干的活移出上下文，卡大了又浪费。
按轮保护在语义上是对的：没干完的必须完整，干完了才可以移走。
注意它**不是**"保留最近 N 轮"，而是"只留当前轮的那条用户消息，其余全部移出上下文"，
上一轮的用户消息也会被移走。

token 也没有退出：它仍然决定"要不要折叠"（阈值）和"折叠后够不够小"（验收），
只是不决定"折叠到哪一条消息"。切点交给语义单位——轮，以及工具调用组。
所谓"更完整"，指的不是"轮比 token 保存得多"，而是**不拆散语义单元**：
一条 assistant 发的多个工具调用和它们的结果必须同进同出；正在跑的轮次不能被移出上下文；
同一条消息不会这次留、下次移。反过来，按 token 预算留尾部的问题不是"留得少"，
而是它可能把一轮从中间切开，而切点合不合法跟留多少 token 没有关系。

代价是如果某一轮本身巨大（比如一次读了十个文件），它可能自己就撑爆窗口；
这时它会退一步，在这一轮内部折叠到已闭合的位置，但绝不会把一个未完成的调用移出上下文。

**三、切点只能落在工具调用闭合的地方。**
模型看到的对话有结构：assistant 发调用，tool 回结果。
在中间切开会留下一个"发了调用没人答"的悬空回合，provider 会直接拒绝；
即使不拒绝，恢复流程也会拿到一个结果已经不在记录里的事务。
所以这是一条正确性约束，优先级高于所有省钱的考虑。

**四、第二次折叠要等新增历史攒够。**
第一次折叠之后，前面的历史已经变成一张便条，再折叠一次还是那张便条，不会多移走一个字节。
第二次折叠真正能新移走的，只有上次边界之后新长出来、且已经干完的那一段。
而被移走的 token 本来是按缓存命中价出现的，很便宜；折叠却让 system 之后整段变成未命中，
要按原价重算。移走得太少，这一次性成本就摊不回来。
所以门槛看的是"新增量"而不是"总量"。
门槛跟着窗口缩放，有上下限，并且不能超过触发线的一半，
否则小窗口永远凑不够，会话再也不会折叠。
代价是某些情况下会"顶着阈值跑一段时间"，这是故意的——宁可慢一点，不要白花钱。

**五、折叠结果不够小就不装。**
装一个"看起来折叠过、其实没省"的检查点，会同时付三份代价：
打碎一次缓存、多一次版本变更、下一轮立刻又超阈值再折叠一次。
所以它有一整套拒绝条件，而且很多在花钱之前就能判定：
固定前缀加上必须保留的内容本身就超线，那折叠也没用，直接拒绝，连模型都不调；
候选不够小，拒绝；候选仍然在触发线上，拒绝，因为那等于给下一次折叠买单；
内容跟上次折叠后一模一样，直接跳过。
代价是会出现"明明超了阈值却什么都不做"的状态，这是故意的——不做比做错便宜。

## 六、呈现层：为什么易变的都在最后

这一轮发给模型的东西，是这样拼出来的（从前往后）：

| 顺序 | 内容 | 变不变 |
| --- | --- | --- |
| 1 | system prompt（含项目规则、pinned 记忆） | 一次会话内不变 |
| 2 | 检查点（便条 + 保留段） | 只在折叠时变 |
| 3 | 记录里尚未被覆盖的部分 | 只往后追加 |
| 4 | 派生尾巴：宿主上下文、任务 step id、折叠后的进度记录 | **每轮都可能变** |

前 3 段构成**前缀**，第 4 段是**尾巴**。
缓存只认前缀，所以尾巴怎么变都无所谓。

这条纪律反过来约束了系统的写法：
**任何"每轮都可能变"的信息，都不许写进历史。**
一旦写进去，它就变成了前缀的一部分，下一次变化就会打碎缓存。

同样的道理也体现在两个细节上：

- 记忆里的"事实索引"故意不放进 system prompt——
  每记一条事实它就变，它后面的项目规则、技能索引会跟着全部重发；
- 工具返回的图片只保留最新的几张，而且是**攒够三张一次性卸载**——
  卸载一张等于改写一条历史消息，攒着卸可以把"改写点"的移动次数降到三分之一。

## 七、出错时怎么办

三条原则，都是"保守优先"：

1. **证明，而不是信任。**
   检查点能不能复用，不看"它说自己覆盖了多少"，而是看"它覆盖的那一段，
   现在的指纹还对不对"。对不上就作废，宁可多发一次完整历史。

2. **记账，而不是重试。**
   一次折叠失败，就记下"这一代别再自动试了"。
   否则每一轮都会重新付一次钱，而且大概率还是失败。

3. **拒绝，而不是降级。**
   归档写不出来，这次折叠就算失败，不会退化成"写一段摘要凑合"。
   因为一旦允许降级，信息损失就从"可恢复"变成"不可恢复"。

---

## 八、它放弃了什么

一套设计好不好，要看它明确放弃了什么：

| 放弃 | 换来 |
| --- | --- |
| "压缩后模型一定知道要点" | 零信息损失，判断权在模型手里 |
| "任何窗口都能压" | 边界永远合法，不会给 provider 悬空调用 |
| "压缩是免费的" | 前缀尽量长期稳定，命中率高 |
| "超阈值必须马上处理" | 不装无用的检查点，不做净亏的折叠 |
| "归档后仍能精确定位" | 简单、可验证、按内容寻址（代价是位置寻址没有索引来源） |

最后一条是个真实的粗糙处：`recall` 工具支持按位置召回，
但归档便条里已经不生成位置索引了，所以按位置召回缺少"怎么知道是第几条"的来源。
按关键词搜索仍然可用。

### 8.1 归档不是无条件更好

归档保住了信息，但把"注意力"交了出去。模型要拿回一段内容，得同时满足三个条件：

1. 它意识到自己缺东西；
2. 它知道该搜什么（关键词、路径、报错片段）；
3. 它有能力读（工具在、文件没丢、读回来不会又把窗口撑满）。

任何一条不成立，归档就等于没存。典型失败是探索性任务：模型不知道自己缺什么，于是不去读，
开始重复劳动或者猜。

摘要的优势恰好在这里——它把"综合"提前做完了。当下一步需要的是"整体结论"而不是"某条细节"时，
让模型去十几万字里搜，往往比给它一段已经组织好的要点更贵、也更容易跑偏。

所以真正的取舍不是"归档 vs 摘要"，而是：

- **归档保信息，不保注意力**；
- **摘要保注意力，不保信息**。

Reasonix 敢选纯归档，前提是它的场景是 coding：需要回读的东西基本都可定位
（文件、命令、报错），用关键词就能搜到。换成"总结这三个月的产品决策"这类任务，
纯归档就不合适了。

---

## 九、如果只记三句话

1. **记录只追加，呈现每轮现拼**——压缩变成"换眼镜"，不是"销毁信息"。
2. **平时不改历史，改就只改一次，且只改最前面**——因为缓存只认前缀。
3. **所有易变的东西放末尾**——这是"高命中"最便宜的一条，不需要任何 provider 特性。
