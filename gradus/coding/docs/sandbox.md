# 沙箱：边界画在哪，为什么画在那儿

这篇讲**思路**：一个 coding agent 为什么要沙箱、每一层边界实际挡住了什么、代价是什么、
哪些约束是不能动的。规格条目在 `design.md` §5.5 / §5.5.1，踩过的坑在 `problem.md`，
这篇不重复它们，只解释「为什么是这样」。

一句话版本：

> **沙箱挡的是「模型手滑把自己的机器搞坏」，不是「有人在攻击你」；它换来的东西是
> 「可以放心让 agent 自己跑」，代价是「它看到的世界是一份副本」。**

---

> 六家 harness（codex / pi / DSH / hermes / reasonix / claude-code）的沙箱做法与对比见
> [sandbox_reference.md](sandbox_reference.md)；本文只讲 Gradus 自己的选择。

## 1. 到底要防什么

把可能的坏事按严重程度排一下，会发现它们需要的防御手段完全不同：

| 坏事 | 例子 | 谁该负责 |
| --- | --- | --- |
| 模型改坏工作区 | `git reset --hard`、覆盖没提交的文件、删目录 | **副本 + 合并**（沙箱） |
| 模型改坏工作区之外 | 写 `~/.bashrc`、改 `C:\Windows`、往 `%TEMP%` 里塞东西 | **受限令牌 / 容器**（沙箱） |
| 模型读到不该读的 | `~/.ssh/id_rsa`、`.env` 里的 key、浏览器 cookie | **只在强隔离下才算解决**（docker） |
| 模型联网 | 下载脚本直接执行、往外传数据 | **只有 docker 能真断网** |
| 恶意代码主动越狱 | 提权、内核漏洞、绕过 AppContainer | 不在这一层的射程内 |

结论要先说清：**我们做的是第一、二档**，第三档在 `docker` 下顺带成立，第四档只有
`docker` 能做到，第五档不在射程内。所以不能对外宣称「沙箱」，只能宣称「写边界」。

这个定位决定了两个看起来奇怪的选择：

- **命令审批不能因为「有沙箱」就放开**：`restricted` 不阻断网络，模型仍然能 `curl | sh`；
- **文件工具不经过沙箱**：见 §4，边界画在进程上，不画在工具上。

---

## 2. 一个会话的沙箱长什么样

时序上有五步，每一步都在解决前一步留下的漏洞：

1. **建副本**：`workspace.py` 在 `%TEMP%` 下建一份 workspace 的副本（worktree 或整树复制）；
2. **起环境**：`sandbox.py` 按后端准备执行环境（受限令牌 / AppContainer / 容器 / 就用宿主）；
3. **绑路径**：文件工具、命令工具、权限策略的 workspace 全部换成副本，系统提示里的 `cwd` 也是副本；
4. **跑工具**：命令与 `codemode` 走 `Environment.spawn`，文件工具仍是宿主进程（见 §4）；
5. **收尾**：先合回宿主，再撤授权 / 销毁容器，最后删副本。

顺序不能换。合回要用副本里的 git 状态与文件，所以必须在副本还在的时候做；撤销 ACE 需要
目录还存在，所以必须在删副本之前做。`sync() → aclose() → discard()` 这条链是契约，不是
建议（`design.md` §5.5.1）。

副本这件事本身就是一层防御：即使模型在副本里 `rm -rf .`，宿主也要等到关闭时才可能受影响，
而合并逻辑只认「新增 / 修改 / 删除」这三种明确的变化，不做整树覆盖。

## 3. 四种边界，各自的机制

`auto` 的挑选顺序是 `restricted → appcontainer → docker → local`：先挑**零安装**的，
再挑需要守护进程的，最后才回落到没有隔离的宿主。理由很实际——沙箱最大的敌人是「用不上」，
一个需要装 Docker 才有边界的工具，用户会直接关掉它。

> **`docker` 后端的当前状态（2026-11 决定）**：**不做真机验证**。代码与离线测试保留，
> 起容器 / 挂载 / 断网 / 退出清理 / 孤儿清理这几项没有实机契约。跨平台不是当前目标；
> 真要启用时，按本文末尾的实机契约跑一遍即可。`auto` 在本机仍然会先选 `restricted`。

### 3.1 `restricted`：只收窄写

这是 Windows 上的目标后端，也是「零安装」的那一档。它的机制可以拆成三件事：

**一个合成 SID。** 每个会话随机生成一个 `S-1-5-21-<4 个随机数>`，这个 SID 不对应任何
真实账户，只在本次会话的副本与 scratch 目录上被授「修改」。会话结束、目录删除，授权自然
消失——所以这个后端**没有持久状态**，不需要 profile、不需要记授权表、不需要清理命令。

**一份受限令牌。** 以当前进程的主令牌为底，调 `CreateRestrictedToken`：

- `DISABLE_MAX_PRIVILEGE`：去掉一切特权（关掉备份/还原、调试之类）；
- `LUA_TOKEN`：做「降权过滤」，`Administrators` 变成 deny-only，等于以普通用户身份跑；
- `WRITE_RESTRICTED`：**写**访问要做第二次检查，这次的 SID 清单是
  「合成 SID + logon SID + `Everyone`」。

前两个决定了「以谁的身份跑」，第三个决定了「能写到哪」。关键在 `WRITE_RESTRICTED` 的语义：
**只有写访问会去查受限 SID 清单，读访问不查**。于是：

> 读：跟当前用户一致；写：必须同时满足「普通 ACL 允许」和「受限 SID 清单允许」。

这就是设计里那句「读按当前用户，写只落在圈内」的来处。它是个**有意的取舍**：模型经常要读
`node_modules`、系统头文件、Python 安装目录，全拦掉会让它寸步难行；而写是最容易造成
不可逆后果的动作，所以只收窄写。

合成 SID 为什么不能换成当前用户 SID？因为一旦放进去，用户能写的地方就全部放行了——那等于
沙箱失效。这一条是硬约束。

**一次显式授权。** 副本与 scratch 上各加一条 `(OI)(CI)M`（继承的可修改）ACE，给合成 SID。
授权本身是宿主侧的辅助进程做的（见 §7 的坑），因为它需要 `WRITE_DAC`，而沙箱里的进程不该有。

顺带解决的环境问题：子进程只拿到一个**最小环境块**——`PATH`、`SystemRoot`、`COMSPEC` 这些
必须有的，加 `TEMP` / `TMP` / `APPDATA` / `USERPROFILE` 全部指向 scratch。宿主里的
`GRADUS_API_KEY` 之类不会漏进去；工具想往 `%TEMP%` 写，会落到能写的 scratch 里。

### 3.2 `appcontainer`：系统自带的容器（已弃用）

用 Windows 的 AppContainer：一个 profile 对应一个 SID，进程没有 capability 就没有网络，
文件访问按授过的路径来。它比 `restricted` 强（连读和网络都能拦），但坑多：

- 没有 Git Bash，只能注册 `powershell`；
- `Remove-Item` / `cmd del` 一律 `Access is denied`，删文件必须走 `[System.IO.File]::Delete()`；
- 解释器目录要递归授权，conda 那种几十万文件的根目录授权一次要几分钟，所以只授必要子树并写
  「已完成」标记跳过重算；
- profile 会残留，需要按 owner 进程判断后清理。

现在它被冻结：`warnings.deprecated` 标记，只保留可用、不再演进，新能力只进 `restricted`。
原因很直接——两个后端维护成本翻倍，而 `restricted` 覆盖了 Windows 上绝大多数需求。

### 3.3 `docker`：真的隔离

长驻容器 + `docker exec`，workspace 挂到 `/workspace`、临时目录挂 `/gradus-tmp`、codemode 的
harness 只读挂进去。默认断网，限制内存 / CPU / 进程数，不继承宿主环境变量。超时直接丢容器，
下次重建。

它是唯一能兑现「断网」的档位，但需要 Docker 守护进程、启动慢、跨挂载路径的坑多，所以排在
`restricted` 后面：**默认给零安装的写边界，需要网络隔离时显式选它。**

### 3.4 `local`：没有边界

直接在宿主上跑，权限就是用户权限。保留它是因为：开发和调试需要、没有可用后端时总要能跑
（`auto` 会回落并给出 `sandbox_warning`），以及 docker / 受限后端不可用时不能让整个工具集消失。

## 4. 边界画在进程上，不画在工具上

这是最容易被误解的一点：`read_file` / `write_file` / `grep` / `glob` 这些**文件工具不走沙箱**，
它们在宿主 Python 进程里跑，权限就是当前用户的权限，只是路径被绑到了副本上。

为什么这样设计：

- 文件工具是进程内的，没有「起一个受限进程」这回事；为它们单独造一套受限 IO 是另一项工程；
- 它们操作的是副本，本来就在圈内，加一层没有额外收益；
- 命令与 `codemode` 才是「任意代码」入口，边界应该卡在那里。

代价要讲清楚：

- **模型能用 `read_file` 读到命令读不到的东西**（比如只有用户 SID 授权的目录）；
- 反过来，命令能做的事（跑任意程序、联网）文件工具做不了；
- 所以「沙箱」这个词对 Gradus 只对**命令类工具**成立。

同理，MCP server 也不在边界内：stdio server 由 MCP SDK 在宿主起进程，只有缺省 `cwd` 会被
换成副本（让相对路径一致），它本身仍是宿主权限、默认可联网。这属于已知缺口，不是疏忽。

---

### 4.1 谁在箱内，谁在箱外

判据只有一条：**是不是我们亲手 `spawn` 的进程**。沙箱是加在「起进程」这一步上的，
所以：

| 东西 | 在箱内 | 说明 |
| --- | --- | --- |
| `bash` / `powershell` | ✅ | 走 `Environment.spawn`，受限令牌 / AppContainer 都作用在它上面 |
| `codemode` 脚本进程 | ✅ | 同上（脚本内部的 `tools.*` 调用回到宿主执行，但脚本本身在箱内） |
| `read_file` / `write_file` / `edit` 等文件工具 | ❌ | 在宿主进程里跑，只是**路径绑到副本**、写操作受权限策略约束 |
| **MCP server（stdio）** | ❌ | 由 MCP SDK 在宿主起进程，**沙箱管不到** |
| MCP server（HTTP / SSE） | ❌ | 本来就是远端服务，连「进程」都没有 |

### 4.2 MCP 为什么不在箱内，以及这意味着什么

MCP server 是第三方代码：`npx @modelcontextprotocol/server-github` 这类命令由 SDK 在宿主
起子进程，用的是**当前用户权限**。它不看副本、不看受限令牌，所以：

- **能读写宿主的任何文件**（不是副本里的那份）；
- **能联网**（`restricted` 本来也不阻断网络，这一点它和宿主进程一致）；
- **能读环境变量与凭证**，取决于 SDK 传了什么（stdio server 的 `env` 由 SDK 白名单过滤，
  只带 `PATH` 一类基础变量，再并上配置里显式写的 `env`）；
- 它吐回来的**结果会进上下文**，但那只是数据，跟隔离无关。

也就是说：**装了 MCP 的会话，隔离强度由那个 MCP server 决定，不由 Gradus 决定。**

### 4.3 我们有的那几道闸

不是完全没有防护，但要说清它们防的是什么：

| 闸 | 防什么 | 防不了什么 |
| --- | --- | --- |
| 项目级 `mcp.json` 必须显式信任（`.gradus/trusted.json`） | 别人仓库里塞的 server 不会自动跑 | 你自己点了信任之后的行为 |
| 用户级 `~/.gradus/mcp.json` 视为「你自己写的」 | — | 同目录被别的进程改写的风险 |
| 工具名加 `mcp__<server>__` 前缀 | 模型和人都能一眼看出「这不是内置工具」 | 它执行时的权限 |
| 结果 20KB 中间截断 + 全文落临时文件 | 上下文被撑爆 | 副作用 |
| stdio server 的默认 `cwd` 指向副本 | 相对路径读写落在副本里 | 绝对路径、以及它自己的写操作 |

### 4.4 为什么不做「MCP 进箱」

做得到的做法大概是：stdio transport 改走 `Environment.spawn`、在容器里起进程。代价：

- HTTP / SSE 类型的 server 与「默认断网」直接冲突，要维护域名白名单；
- 沙箱只覆盖 Windows（`restricted`）与 docker，跨平台行为不一致；
- MCP 生态大量 server 依赖网络与本地缓存目录，进箱后大部分会直接不可用。

所以这条留在未定列：**要强隔离，就不要装 MCP**；装了就要按「它在箱外」来评估风险。

## 5. 副本：为什么不是直接在宿主上做

如果只在宿主上加权限控制，模型能看到真实文件、环境变量、`node_modules`、被 gitignore 的
`.env`——这些它本来就该看到。问题出在**写**上：宿主上的写是不可逆的。

副本模型把「不可逆」变成「可审查」：

- 会话期间所有改动落在副本里，宿主一个字节都不动；
- 关闭时按三种明确的变化合回：新增、修改、删除；
- 合并失败不抛异常，保留副本并给出路径，用户自己决定怎么处理。

两个实现细节值得单独说：

**worktree 还是整树复制。** workspace 本身是 git 仓库根时，优先 `git worktree add --detach`：
快、省空间、合并可以走 `git diff` + `git apply`。但 worktree 只检出 HEAD，未跟踪文件
（`.env`、本地脚本、被 ignore 的配置）不在里面，而模型恰恰需要它们——所以建完后会把
`git ls-files --others` 列出的文件复制进去。不是 git 仓库就整树复制，跳过 `.git`、`.venv`、
`node_modules` 这些大目录。

**删除怎么判断。** 「宿主机有、副本里没有」有两种可能：模型删了，或者宿主在会话期间新建了。
复制模式用建副本时的文件清单做基线，只删「基线里有、现在副本里没有」的；worktree 模式下
已跟踪文件的删除由补丁完成，带进来的未跟踪文件单独比对。不这么做会误删用户刚写的文件。

## 6. 生命周期与清理

沙箱带来的最大运维风险不是权限，是**残留**：强杀之后，容器在跑、副本在、ACE 还在。

所以每个产物都带「谁的、什么时候的」：

- 副本旁边一个 `.owner`：pid、用户名、宿主路径、是否 worktree；
- scratch 里一个 `.owner`：创建它的 pid；
- 容器带 `gradus.owner=<pid>` / `gradus.user=<name>` 标签。

下次启动时按 **pid 是否还活着**判断，而不是按时间。pid 被系统复用时最多留下一个旧产物，
不会误删正在用的；用户名不匹配的一律不碰——临时目录可能是机器级共享的。

回收分两条路，因为它们的信息量不同：

| 产物 | 判据 | 谁能区分用户 |
| --- | --- | --- |
| 副本 `gradus-ws-*` | `.owner` 里的 pid + 用户名 | 能（`workspace.cleanup_orphans`） |
| scratch `gradus-tmp-*` / `gradus-rs-*` / `gradus-ac-*` | `.owner` 里的 pid，AppContainer 没有标记就按 7 天 | 不能，只按前缀 + 时间 |
| MCP 落盘 `gradus-mcp-*` | 1 天 | 不能 |
| 容器 | `gradus.owner` 标签 + `docker ps` | 能 |

删除失败只跳过，不影响会话；结果不进 `sandbox_orphans`（那是给用户看的，每次启动刷屏没有意义）。

## 7. 踩过的坑：都是「看起来能用」的那种

这一节是全篇最实用的部分。共同特征是：报错信息骗人、错误被吞掉、或者只在特定机器上出现。

| 坑 | 现象 | 真因 | 现在怎么做 |
| --- | --- | --- | --- |
| 受限 SID 清单只有合成 SID | 进程立刻退出，`0xC0000142`（DLL 初始化失败） | 系统 DLL 的读检查过不去 | 加上 logon SID 与 `Everyone` |
| logon SID 被 `LocalFree` | 关闭会话时 `0xC0000374`（堆损坏） | 它指向 `GetTokenInformation` 缓冲区内部 | 只保活缓冲区，不释放 |
| 用 `icacls *<合成 SID>` 授权 | `no mapping`（1332） | 未注册的 SID 没有名字可解析 | 直接改 ACL 对象 |
| 用 `Get-Acl` 改 ACL | `ACL AddAccessRule failed (exit 1)`，stderr 被吞 | 辅助进程是 Windows PowerShell 5.1，却继承了 pwsh 的 `PSModulePath`（PS7 目录），5.1 加载 PS7 的 Security 模块失败 | 脚本不调 cmdlet；另外给 5.1 一份自己的模块路径 |
| 用 `Set-Acl` 改 ACL | 同上那句，加上 `does not possess the 'SeSecurityPrivilege'` | 非提权令牌改**受保护 DACL** 需要特权 | 改走 `DirectoryInfo.GetAccessControl()/SetAccessControl()`（只要 `WRITE_DAC`） |
| scratch 用 `tempfile.mkdtemp` | `codemode` 一律 `script exited without a result` | `mkdtemp` 建的是受保护 DACL 目录（只授 `OWNER RIGHTS`/SYSTEM/Administrators），受限令牌匹配不上，子进程读不到 scratch 里的脚本 | Windows 上用普通 `mkdir`（继承 `%TEMP%` 的 ACE） |
| 副本放进嵌套子目录 | 沙箱里 `pwd` 是 `C:\`，相对路径全废 | AppContainer 在更深的目录里设不了工作目录 | 副本直接放在 `%TEMP%` 下一层 |

关于 `OWNER RIGHTS` 那一条，值得把结论写死：**沙箱目录必须让人看得见「用户 SID」或
`Users` 组**，不要依赖「所有者权限」这类抽象 ACE。继承 `%TEMP%` 的普通 `mkdir` 通常满足
（`%TEMP%` 本身会给用户 SID 或 `Users` 留口子），`mkdtemp` 一定不满足。具体是
`OWNER RIGHTS` 与降权过滤令牌的哪一步交互导致匹配失败，我们没有钉死——但实测对照很干净：
普通目录能读，`mkdtemp` 目录不能，把 ACE 换成用户 SID 也能。

另一个反复出现的教训：**ACL 辅助脚本的错误必须能被看见**。早期 `_acl` 把 stderr 丢进
`DEVNULL`，于是「授权失败」只剩下 `ACL AddAccessRule failed (exit 1)` 这一句，两次排查都被
它带偏。现在的做法是：辅助脚本只做一件事、出错就抛带路径的异常，调试时把 stderr 捞出来看。

## 8. 不能动的约束

按「违反之后会发生什么」排序：

| 约束 | 违反后的症状 |
| --- | --- |
| 受限 SID 清单含 logon SID 与 `Everyone`，且**不含**用户 SID | 进程起不来，或写边界失效 |
| logon SID 不 `LocalFree` | 堆损坏，关闭时崩 |
| 合成 SID 的 ACE 用 ACL API 加，不用 `icacls` | 授权根本没写进去 |
| 沙箱目录不用 `mkdtemp`（Windows） | 命令读不到 scratch / 副本里的文件 |
| 副本直接在 `%TEMP%` 下一层 | 工作目录失效，相对路径全废 |
| 关闭顺序 `sync → aclose → discard` | 撤销失败、留 ACE 或容器 |
| worktree 必须带进未跟踪文件 | 模型看不到 `.env` 等文件 |
| 带进来的未跟踪文件不进补丁 | 合并整体失败，副本被迫保留 |
| 复制模式用基线判删除 | 误删用户会话期间新建的文件 |

这些条目在 `design.md` §5.5.1 有一张更细的表，每条都对应一个实机断言。

## 9. 怎么验证

沙箱的「能用」不能靠手工试：它涉及令牌、ACL、挂载、合并、清理，任何一处坏了都只表现为
某个操作的某个错误。所以有一份**实机契约**：

```powershell
uv run pytest -q                                                        # 离线：纯逻辑与解析
$env:GRADUS_SANDBOX_LIVE="1"
uv run python -m pytest gradus/coding/tests/test_sandbox_live.py -q -s  # 实机：一次会话里逐条核对
```

实机那组会在一次真实会话里依次确认：副本位置与工作目录、相对路径读写、已跟踪与未跟踪文件
可见、越界读写、`codemode`、删除、关闭时合回（新增/修改/删除）、孤儿副本清理。它跑不过就是
契约破了，不需要再写一次性探针脚本——这正是当初做这份测试的原因。

**离线与实机的分工要清楚**：离线测试能钉住「ACL 脚本长什么样」「工具集怎么拼」「合并规则」，
钉不住「令牌真的起作用了吗」「目录真的可读吗」。这次三个 ACL / DACL 的坑，全都是实机测试
才暴露出来的，而且暴露的前提是先把后端起起来了——在它起不来的时候，那 12 条实机测试一直是
skip 的，看上去一片绿。

## 10. 已知限制

- **`restricted` 不阻断网络**：unelevated 拿不到防火墙规则，因此命令审批不放开；
- **读不隔离**：模型能读用户能读的一切，`.env`、`~/.ssh` 都在射程内（要拦就上 docker）；
- **文件工具与 MCP 不在边界内**：见 §4 与 §4.1–4.2（MCP 是第三方进程，隔离强度由它自己决定）；
- **不做多租户**：同一用户的两个会话共享一份副本逻辑与文件权限，隔离粒度是 OS 用户；
- **`appcontainer` 冻结**：可用但不再演进；
- **`docker` 尚未在真实引擎上跑完契约**：接口与离线断言齐了，实机只跑到 `restricted`；
- **结论对机器敏感**：临时目录位置、目录 ACL、PowerShell 版本、是否提权都会改变观感。同一个
  后端在两台机器上可以一台全绿一台全红（这次就是），所以契约必须在目标机器上跑，别拿另一台
  机器的结论当依据。
